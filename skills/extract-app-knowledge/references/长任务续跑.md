# 长任务续跑（知识规范 0.8.3）

本指导适用于需要跨多个会话或批次提取知识的项目。项目明确给出的范围、节奏和授权优先；本文件不授权批准、发布、推送或接入机器人。

## 状态放在哪里

| 信息 | 权威位置 | 更新时机 |
| --- | --- | --- |
| 范围、仓库与固定提交 | 项目 `知识库配置.json`；范围说明见项目规划 | 基线或范围经确认发生变化时 |
| 模块与入口覆盖 | `知识源/功能大纲.md` | 新入口、归类或模块状态变化时 |
| 当前进度和下一项工作 | 项目进度记录 | 每完成一个模块或处理一个阻断后 |
| 跨模块共用结论 | 项目共用事实记录（有交叉结论时） | 结论、证据或消费模块变化时 |
| 未解决的证据与业务问题 | 模块 `待确认事项.md` 和项目级缺口记录 | 发现、解决或改变影响范围时 |
| 审核与发布状态 | 每模块 `发布清单.md`、项目 Git、`发布/` | 准备、批准、发布或回退时 |

聊天总结和人工报告用于沟通；续跑时从这些文件及 Git 重新核对状态。项目不必为了本指导复制多份并行的进度表。动态计数留在项目记录里，不写进长期不更新的启动提示词。

## 空白上下文接手

1. 先读项目给出的接手入口、配置、规划、进度、大纲、共用事实与缺口，再读当前模块的规格和发布清单。没有项目入口时，从 `知识库配置.json`、`知识源/功能大纲.md` 和 Git 状态定位现况。
2. 核对工具包 `VERSION`、项目 `standard_version`、配置中的源码提交、项目 Git HEAD 与工作区；若文档写的版本或进度和实际文件不符，以可验证的项目状态为准，修正记录后继续。源码证据仍只读配置指定的提交。
3. 运行 `check`，区分结构校验通过与语义已核实。查看待批准清单是否仍绑定当前内容；有变化的模块按 `impact`、逐文件语义复核、`confirm-claims`、`prepare --refresh` 重做。
4. 从大纲与进度选择下一项有界工作。缺源码或动态值的入口保持待核查，继续其它可取证模块；不要因聊天里说过“已完成”而跳过文件验收。

## 模块与批次循环

- 逐模块完成固定提交取证、双受众正文、四类静态问答、`check`、`impact`、语义复核、`confirm-claims` 和 `prepare`。更新进度与大纲状态，再按项目约定继续下一模块。
- 对跨模块事实指定取证责任方并列出引用方。事实或锚点改变时，查阅引用方正文，重做受影响模块的结论复核和发布清单；`impact` 清零不能代替阅读自然语言结论。
- 批次边界由项目决定；适合较长全 App 任务的做法是每完成一个业务域或约 5–8 个模块，核对模块与入口覆盖、未归类项、源码缺口、跨模块结论、Git 状态及待审包摘要。批次报告只列本批变化、影响答案的冲突、校验结果和下一项工作。
- 会话压缩或更换执行者时，保留一份简短接力记录，指向权威文件并写明当前 Git 提交、进行中的模块、下一项与阻断。新执行者重新核对文件，不把接力记录当成独立事实来源。

## 审核、发布与完成判定

模块提取完成后可继续其它模块；不要求人逐阶段或逐条结论签字。用户可以在一次回复中明确列名批准多个已审阅且内容未变化的模块包，但工具仍须分别核对并记录每个模块的批准。未获批准的包保持草稿，不因批次报告、口头认可或 AI 自检自动变为已批准。详细发布步骤以 [发布与维护](发布与维护.md) 为准。

发布完成须核对新双版目录、版本清单、当前指针及 `audit-release`；同步到外部产物库或推送远端遵守项目授权和路径约定。全范围完成须对照大纲逐项说明模块、新发现入口、未归类与待核查项、缺源码范围；静态知识完成、内容发布和线上验证分别报告。`check` 不证明真实业务政策、运行效果或盘点穷尽。
