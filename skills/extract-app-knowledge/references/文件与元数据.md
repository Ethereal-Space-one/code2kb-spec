# 文件与元数据（文件协议兼容：c2kb-file/1 与 0.8.3）

## 目录与正文保全

```text
知识源/
  功能大纲.md
  术语表.md                         # 可选
  业务域/子模块/
    模块概览.md
    功能与范围.md
    业务流程.md
    规则与限制.md                   # 有依据才建
    常见问答.md                     # 有问题才建
    业务意图.md                     # 可选；仅发布完整闭环的业务意图
    技术实现.md                     # 研发导航
    接口与调用.md                   # 有接口才建，研发版
    方法与源码.md                   # 有方法才建，研发版
    结构化规格.md                   # 内部
    待确认事项.md                   # 有未知才建，内部
    发布清单.md                     # 模块一次批准，内部
运行证据/业务域/子模块/中文记录.md  # 内部
自动审核策略/策略名.json             # 可选；项目固定预授权策略
自动审核记录/运行ID/模块ID.json      # 可选；不进入检索目录
发布/
  当前版本.json                    # 机器当前入口
  当前版本.md                      # 人读导航
  版本清单/当前版本号.json          # 当前双版摘要；历史清单在 Git 中
  业务版/                          # 固定路径，完整业务正文、导航、检索索引
  研发版/                          # 固定路径，同一业务正文、研发正文、导航、索引
```

五类常规业务正文、可选业务意图、三类研发正文与过程稿各有用途。索引只提供定位，发布器逐字复制正文。默认业务域/子模块两级；多个独立可检索和维护的场景才加一层场景目录。场景文件复用 module_id 并填 scene_id，模块根保留概览、规格和研发索引；不同页面、按钮或角色本身不构成加目录的理由，不建空文件凑格式。

`发布/` 是当前快照，不在工作树内平铺保存历史版本。每次发布完整替换上述固定目录；覆盖前旧快照必须已提交到 Git，历史查看和回退使用发布提交或标签。

## 文件元数据

每篇知识源 Markdown 使用单层 `key: value` front matter；不支持嵌套 YAML或多行值。中文名称供人阅读，稳定 ID 供机器关联。

```yaml
---
module_id: example.module
document_type: flow
review_status: draft
applicability: current
---
```

文件与类型固定对应：模块概览→overview、功能与范围→scope、业务流程→flow、规则与限制→rules、常见问答→faq、业务意图→intent、技术实现→implementation、接口与调用→api_catalog、方法与源码→method_catalog、结构化规格→spec、待确认事项→questions、发布清单→release_manifest。根功能大纲为 outline，根术语表为 glossary。

状态为 draft/reviewed/policy_reviewed；适用性为 current/superseded。`reviewed` 只表示人明确批准，使用 reviewed_by 与 reviewed_at。`policy_reviewed` 表示通过项目预授权策略，使用 review_mode、review_policy、policy_version、policy_owner、executed_by、reviewed_at、review_evidence 及两个摘要字段，不得混入 reviewed_by。两种状态都必须与发布清单快照一致才能发布。`prepare --refresh` 清除该模块旧审核戳并恢复 draft；未列入发布包的同模块旧正文也恢复 draft，内容不删除。可选根术语表仍用文件审核。

业务文件元数据只用 module_id、scene_id、document_type、review_status、applicability、reviewed_by、reviewed_at、aliases，以及策略审核专用字段 review_mode、review_policy、policy_version、policy_owner、executed_by、review_evidence、review_evidence_digest、policy_digest。正文不含接口、类、SQL、源码路径、commit、API/METHOD ID或内部/技术文件链接。用户文案是命名线索，代码现状不自动定义业务政策；动态配置、平台结果和实际运行不确定时用业务语言写清回答边界。

研发文件填写 runtime_status: source_only/runtime_verified/verified_deployment。后两者分别需要 runtime_evidence（EVID ID，逗号分隔）或 deployment_evidence（部署 EVID ID），正文限定实际证明的场景，不自动把一条运行证据推广到全模块。模块规格与研发文件使用按仓库 ID 排序的 source_revisions：`source_a=GitSHA, source_b=GitSHA`。仅列模块实际取证仓库，与配置吻合；单侧证据限缩为单侧事实，不冒充完整跨仓调用。

业务意图文件只保留已经闭环的业务原因和影响，不写 INT、EVID、fact_id、接口、源码路径或 Git 提交。未确认业务意图留在规格与待确认事项。业务证据仍放在项目 `运行证据/`，原始材料不进入 Git；格式见[业务意图与材料证据](业务意图与材料证据.md)。
