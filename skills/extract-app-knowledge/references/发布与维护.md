# 发布与维护（文件协议兼容：c2kb-file/1 与 0.8.3）

Code2KB Spec 工程版本、知识规范版本和内容 `release_id` 分别演进。版本清单记录 `standard_version`、`release_id`、文档提交和参考实现版本用于溯源；工程版本与知识规范编号不要求相同。旧内容与旧发布结构通过 Git 提交或标签恢复。

源码仓库 path 可写绝对路径，也可写完整的大写环境变量引用以适配本机和 CI。参考实现直接读取变量，不经过 shell；变量必须指向已存在的绝对目录。固定 commit 仍写入配置，不从环境变量或分支名读取。audit-release 只核对发布快照，离线审计时不要求源码路径变量存在。

## 运行依据与发布

证据单独放项目 `运行证据/`，类型 runtime_evidence。运行、业务、部署证据分别为 runtime/business/deployment。运行与部署证据填写模块、限定 fact_ids、来源、环境、源码基线、观察日期及有效期/重新核对条件。兼容协议的业务证据使用材料来源、定位、原始内容摘要、脱敏摘录模式和 intent_ids；人工确认另填确认身份、日期和边界。过期证据不能作为当前发布依据；历史记录标 applicability: superseded。单项验证不自动认证整个模块。

prepare 绑定正文、规格、已有待确认事项和候选实际引用的证据，生成发布清单与 review_subject_digest，并把该模块旧审核状态恢复为 draft。兼容协议清单同时记录 `intent_included`；使用 `--files` 排除意图正文时为 false。人一次确认正文、关键未知与边界时，approve 转写真实原话；项目已有预授权策略时，policy-review 校验本次记录并写入独立的 policy_reviewed 状态。AI 建议或 check 通过本身不构成人工批准或策略审核。修订使摘要变化时重新准备受影响模块包，不重开全链审批。

发布时相关输入与独立文档 Git HEAD 内容相同；版本清单记录文档提交、固定双版路径和逐文件摘要。完整正文逐字复制，原有三级导航与功能大纲保留，额外生成检索索引。候选双版全部通过后，工具整体替换 `发布/`；工作树只保留当前快照，历史版本由 Git 提交或标签管理。已有 `发布/` 未完整提交时拒绝覆盖。`audit-release` 检查当前快照的增删改。私钥等高置信模式及可选 sensitive_patterns 发布前扫描，只输出文件位置。

正文五类与研发三类的必要性仍按有证据的内容判断；新增索引、清单、结论记录不替代正文。机器人按当前版本与受众读索引，再读相关文件标题段，内部规格、问题、发布清单和运行证据不进入机器人检索目录。检索、工具、缓存与会话权限需分别配置。

## 从提取到模块批准

先完成大纲和模块正文。运行证据不是初次提取的必填前提，缺证据就保持 source_only。AI 完成四类问答后运行 impact，逐文件核对相同主题；confirm-claims 记录已完成的复核，不执行语义推理。prepare 生成一个模块的可审发布包。随后选择人工 approve 或策略 policy-review，提交全部发布输入，再 publish。

```bash
python3 validation/knowledge.py impact --project-root /项目 --module-id example.module
python3 validation/knowledge.py confirm-claims --project-root /项目 --module-id example.module
python3 validation/knowledge.py prepare --project-root /项目 --module-id example.module --business-topics '用户操作、处理结果' --business-unknowns '运行环境差异' --business-keywords '订单、查询' --engineering-topics '调用链与处理方法' --engineering-unknowns '部署与运行效果' --engineering-keywords '订单、查询、实现'
```

填写 `--business-keywords` 与 `--engineering-keywords` 时，按[知识写作与复核](知识写作与复核.md)的选词规则，从有正文依据的主题选取并消歧；关键词只供检索定位，不替代主题、未知边界或正文。

prepare 默认包含当前模块全部业务/研发正文；部分发布时用 `--files '模块概览.md,功能与范围.md'`，也可列场景相对路径。已有清单要更新时显式 `--refresh`；更新后为 draft。过程稿自动列作审核依据，不发布。`--business-*` 只进业务版索引；`--engineering-*` 只进研发版索引，省略时复用对应业务值。

存在完整业务链时，`业务意图.md` 默认随候选进入业务版与研发版；未确认 INT 不会生成该文件。意图正文可被 `--files` 明确排除，清单会固定记录本次决定。业务证据始终不进入发布目录。

兼容协议正文提到另一 Markdown 文件时必须使用能在同受众发布目录内解析的链接；内部过程文件不发布，应就地说明，不留纯文字文件名指针。研发正文中的事实 ID 必须在本模块规格中定义；跨模块引用写作 `module_id#fact_id`。发布器按已审核规格在研发版生成《事实编号对照》，并从大纲及运行依据生成发布范围数字。配置 `boundary_notes` 只写定性说明，不手填覆盖数量。

人工模式收到人的明确批准后使用真实审核人、日期和原话。条件式建议、其他 AI 回复或模板名不构成授权；命令不能认证身份。

```bash
python3 validation/knowledge.py approve --project-root /项目 --module-id example.module --reviewed-by '实际审核人' --reviewed-at 2026-10-14 --approval-note '人已明确确认的原话与发布边界'
python3 validation/knowledge.py check --project-root /项目
```

策略模式先在配置中启用并固定一份已经提交的策略。策略至少要求参考实现内置的结构检查、impact 清零、四类问答、源码追溯、跨模块一致性和敏感扫描；其它检查用 external.* 并提供报告摘要。prepare 输出的 review_subject_digest 写入本次审核记录后执行：

```bash
python3 validation/knowledge.py policy-review --project-root /项目 --module-id example.module --evidence-file 自动审核记录/run-id/example.module.json --executed-by ci-bot
```

配置与策略在 policy-review 前必须与 Git HEAD 一致。新审核记录使用 `1.1`；若策略要求 `external.*`，每份外部报告须先脱敏，保存为项目 `自动审核报告/` 下的 JSON，提交后在记录中填写 `path` 和文件原始字节 SHA-256。工具复算摘要并核对 Git HEAD，不判断报告结论真假；旧 `1.0` 记录只用于历史复核。策略过期、风险超限、检查缺失、摘要或源码基线不符、执行者冒充策略所有者、或发现命中人工门禁时均拒绝。策略审核不调用模型、不提交 Git、不把 source_only 改成运行验证。审核后把正文、规格、清单和记录一起提交；publish 会再次校验并把审核模式写入版本清单。

未列入模块包的旧 reviewed/policy_reviewed 正文恢复 draft，内容保留。正文、规格、自测、运行依据、主题或未知范围变化都会使审核快照过期。AI 修正后刷新发布包，集中呈现改变的答案，不要求逐阶段签字。

## Git 与完整发布

新项目初始化独立文档 Git 仓库，可复用 `templates/文档仓库.gitignore` 并设置自己的 Git 身份。提交配置、大纲、本次正文、规格、待确认事项、发布清单和相关运行证据；策略模式还须提交固定策略和本次审核记录。工具包不自动提交。publish 只检查本次相关输入与 HEAD 一致，无关便笺或未发布模块正文变化不因此失效。

```bash
git -C /项目 init
git -C /项目 add 知识库配置.json 知识源
git -C /项目 commit -m '记录已确认的知识发布输入'
python3 validation/knowledge.py publish --project-root /项目 --release-id example-v1
```

运行证据存在时另将运行证据目录加入提交。发布后必须把整个 `发布/` 提交，旧版本才能由 Git 恢复；document_commit 指构建输入的既有提交，不制造相互引用的 Git SHA。

publish 在临时目录生成两版完整正文、三级目录、功能大纲、发布信息与检索索引，正文逐字复制。业务版没有内部过程稿或技术正文；研发版复用业务正文并保留相关接口/方法。固定输出为 `发布/业务版` 和 `发布/研发版`；兼容参数 `--business-out`、`--engineering-out` 即使显式传入也只能是这两个路径。生成、敏感扫描或安装后审计失败时恢复原 `发布/`。

`发布/版本清单/<当前版本>.json` 保存当前产物摘要与文档提交；下一次发布时随完整快照一起替换，旧清单留在 Git 历史。`发布/当前版本.json` 是机器唯一当前入口，`当前版本.md` 为人读导航。治理文件不加入业务检索目录；发布版额外出现文件也会被检查发现。

```bash
python3 validation/knowledge.py audit-release --project-root /项目
git -C /项目 add 发布
git -C /项目 commit -m '发布知识库 example-v1'
git -C /项目 tag kb-example-v1
```

不带 ID 的 `audit-release` 检查当前指针与双版；带 ID 只能检查当前工作树中仍存在的清单。发布完成后必须提交 `发布/`，建议以 release-id 创建 Git 标签。下一次发布会先确认当前 `发布/` 已提交，再覆盖固定目录。

兼容协议的 `audit-release` 可在只有 `发布/` 的最终 KB 仓库运行，不要求存在 `知识库配置.json`、`知识源/` 或源码路径。当前指针和版本清单使用严格 JSON，重复字段、未知字段、清单结构版本、审核溯源或逐文件摘要不一致都会失败。

回退不再使用 `activate`。回退上一提交优先用 `git revert <发布提交>`；恢复任意标签时，从标签恢复整个 `发布/` 后创建一条新的回退提交，再用该标签对应的 Code2KB Spec 版本运行 `audit-release`。不要只恢复业务版或研发版，以免指针、清单与双版不一致。机器人始终索引固定路径，发布或回退后重建索引即可。

## 检索与 token 输入

先读受众版检索索引：关键词→模块→文件→标题。只加载与问题相关的正文段落，必要时向同模块扩展。索引覆盖所有发布正文和标题，不承载唯一结论，不能只用索引摘要回答。研发群可读接口和方法；业务群的检索、工具和缓存只访问业务目录。

脚本生成导航，不实现向量检索、chunk 切分或机器人调用。实际 token 节省和召回率在接入后用真实问法验证。

## 运行、业务与部署证据

按模板保存运行证据/业务域/子模块/中文记录.md，使用 EVID ID。必填 evidence_type、module_id、fact_ids、source_revisions、environment、observed_at 及四个章节。valid_until 可选；没有可靠期限时写明何种部署/配置变化触发重核，勿沿用示例日期。历史证据可标 superseded。

RUN_VERIFIED 用运行或部署 EVID，BUSINESS_CONFIRMED 用业务 EVID。证据覆盖相应事实、模块和基线；观察日期与审核日期是两回事。引用过期证据发布会失败。发布包绑定证据摘要，修改证据需刷新包。

研发文件可以保持 source_only 并仅在部分结论引用运行证据。runtime_verified 要列 runtime_evidence IDs 并限定证明场景；部署组合有证据才用 verified_deployment/deployment_evidence。单项观测不扩张为全模块线上可用。
