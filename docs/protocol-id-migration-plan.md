# 公开文件协议编号迁移计划

> 状态：设计稿，尚未改变当前 `0.8.3` 校验行为、模板、已发布标签或任何使用方知识项目。工程发行版本由独立发版流程确定，不与下述协议编号绑定。

## 目标与编号

为开源文件协议采用带产品命名空间的兼容标识，建议新标识为 `c2kb-file/1`。`0.8.3` 作为已公开的旧标识保留读取和审计支持；新项目模板只写新标识。这里是**兼容标识重编**，不借此改写业务事实、审核语义或目录结构。若迁移实施时发现实际格式差异，须另列变更和夹具，不能宣称只换编号。

## 行为矩阵

| 对象 | 旧标识 `0.8.3` | 新标识 `c2kb-file/1` |
| --- | --- | --- |
| 新项目模板 | 不再默认生成 | 默认生成 |
| `check`、候选准备与发布 | 保持支持，不暗中重标 | 支持 |
| 已发布版本清单与当前指针 | 按原标识逐文件审计，内容不改 | 按新标识审计 |
| 业务意图等已有能力 | 按结构和能力检查，不因旧数字而关闭 | 同样检查 |
| 不认识的标识 | 拒绝，列出受支持标识 | 拒绝，列出受支持标识 |

旧发布目录、版本清单和标签必须保持原字节与摘要。审计旧版本不依赖当前工作项目配置中的新标识，也不要求旧项目先迁移。

## 显式迁移命令

提供仅针对**知识项目工作源**的 `migrate-protocol --project-root ... --to c2kb-file/1 --dry-run` 与显式执行模式。先列出将改动的配置和受影响候选、审核快照；拒绝未知旧标识、未提交改动、符号链接和无法证明的状态。执行时只改有定义的源配置与必要元数据，不触碰 `发布/` 下既有快照，不自动批准或发布。若候选摘要受影响，逐包重新准备并按现有审核规则处理；下次发布必须使用新 `release_id`。执行前后均可审计旧版本。

## 实施顺序与回归

1. 冻结新旧标识的规范要求和兼容矩阵；列出 `standard_version`、`spec_version` 在配置、校验器、模板、示例、一致性夹具、版本清单与指针中的写入/读取点。
2. 将“当前新项目标识”与“支持读取的旧标识”拆开；消除以 `== STANDARD_VERSION` 推断功能是否可用的分支。
3. 为新旧项目分别提供有效/无效夹具，并验证 `check → prepare → approve → publish → audit-release`；旧格式发布物仅审计，不重写。
4. 实现先干跑后执行的显式迁移，测试中断、重复执行、已有发布、候选审核失效和回退到原 Git 提交。
5. 更新规范、模板、兼容声明、CLI 版本输出与技术文档；新协议编号只在技术契约与确实发生协议变更的发布说明中出现。
6. 在独立公开样本上做新旧对照，通过完整 CI 后以新工程版本发布。不得修改 `v0.2.0` 至 `v0.6.0` 标签，也不得触及本地 Kit 或使用方 KB。

**完成标准**：新项目默认新标识；旧项目在不迁移时仍可检查、发布和审计；迁移仅经显式执行并产生可审阅差异；旧发布物摘要不变；未知标识仍失败封闭；两个版本体系在全部对外材料中可单独解释。
