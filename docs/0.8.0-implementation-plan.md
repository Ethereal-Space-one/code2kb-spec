# Code2KB Spec 0.8.0 发布规划

> 状态：实现候选，待独立审查和发布门槛。基线为已发布的 `v0.7.0`。本计划只针对开源工程和可公开使用的样本；不读取、复制或改写任何使用方知识项目。工程版本、知识文件协议和知识项目发布版本继续独立演进。

## 1. 本版要解决的问题

Code2KB Spec 的产物是从固定源码提交提取的**业务行为与代码逻辑知识**，最终供检索定位和问答组合。源码升级后，维护者首先需要知道：哪些已发布结论的证据可能失效，哪些检索内容要复核，以及哪些变化因关系不完整而不能排除影响。

现有 `preview-upgrade` 只检查**单模块关系映射中已有的证据锚点**，在新提交的原路径、原行段重新取片段，报告受影响事实和主题。它不盘点整个提交差异，无法发现新文件、新入口、未建立关系的调用或仅因移动而失去定位的证据；现有 `impact` 主要处理知识工作源的变更。0.8 在两者之上增加**全项目、只读的源码升级影响计划**，不再造一套事实或审核流程。

独立的[检索产物结构审查](0.8.0-index-readiness-review.md)发现一个更靠近最终用途的前置风险：发布正文拆为检索单元时，适用条件、回答和未知边界可能分离。0.8 先保证生成单元可被有效索引且保留完整答题限定，再让源码升级影响计划定位这些单元；两项共同构成本版发布门槛。

本版的完成标志有两项：在固定公开验收场景中，命中的生成单元保留回答所需的条件和未知边界；给定旧、新固定提交，工具能解释“变化 → 证据/覆盖状态 → 待复核事实 → 业务与研发正文 → 检索主题/单元”，并把无法归属的变化显式列为缺口。维护者据此决定复核范围；工具不得把预览结论当成新的已证实事实。

## 2. 交付范围

### 2.1 检索产物结构与导入契约

- 维持“基础双版默认发布、检索扩展显式启用”的边界。针对生成器而非手写夹具，验证一个回答单元是否同时带有决定答案的适用条件、例外、失败与未知；若边界需跨节获取，安全聚合或阻止其作为独立可答单元通过门禁。
- 在现有 `topic` 与正文中保留可读模块名与父标题路径，不新增强制元数据字段；“说明、适用条件、回答边界”等泛标题须带模块或主题上下文。`question_variants` 仍只是保守标题别名，不声称已生成真实问法。
- 本版先提供单独的索引覆盖报告，列出业务术语表等已发布但未转为单元的内容、原因与基础正文位置；根级术语单元的身份设计后续再定；修复拆分后的跨节内部锚点，使其能够返回发布原文或目标单元。
- 给外部 FTS/向量消费者一份最小快照导入契约：按 `audience` 与 `release_id` 隔离，从已审计检索清单读单元，以 `(release_id, audience, unit_id)` 为索引键在独立新快照中写入并校验全集，成功后切换受众的当前快照指针，失败沿用旧快照。集合差用于核对删除项；旧记录不进入新快照，旧快照只在切换成功后按保留策略回收，禁止先删除当前可用记录。本版只提供契约与可执行模拟，不内置生产索引服务。

实现取舍：优先保持现有章节内已经完整的主题；对泛标题和嵌套问答保留父上下文。无法确定限定归属时，保守保留完整来源正文并提示复核；超过单元大小上限则阻止该扩展构建，不截断边界。此规则只保证发布正文文本的保全，不声称程序能自动判断业务语义完整。聚合后在现有 `source_headings` 中保留所有来源节标题，回归关系清单的主题到单元映射，避免仅改显示标题就破坏追溯。额外覆盖/结构诊断使用独立报告，不写入已有严格字段清单。

### 2.2 全项目变更盘点

- 基于 Git 对象比较配置中的旧提交和显式给出的新提交；不读取工作区作为正式源码证据，也不改变项目配置、运行账本或发布指针。
- 列出新增、删除、内容变更的路径及其旧、新 blob；行段变化用于定位既有证据。路径移动或相似内容只给出**重定位候选**，不自动沿用旧 `verified` 锚点或长期组件身份。
- 将每个变化路径归入“有已复核关系覆盖 / 仅有候选或未解关系 / 无关系覆盖 / 明确排除且有理由”。新入口、新文件、动态调用和外部服务变化不能因为旧图中没有节点就被判为无影响。
- 复用 0.7 Adapter 的能力声明辅助发现新增候选；L1 扫描只能证明文件被发现，不能证明业务关系。无法由当前 Adapter 分析的语言和跨仓桥接保持 `unresolved`。

### 2.3 反向影响计划

- 复用 0.5 的证据快照、关系映射与稳定事实/主题 ID，沿**已复核**关系计算直接命中的事实和主题；候选、未解边另列“需扩展取证”，不得用于安全排除。
- 由结构化规格的“影响的知识文件”和主题来源定位业务、研发正文；若现有发布启用了检索及关系清单，再以冻结映射定位对应 `unit_id`。没有检索或关系扩展时报告可达到的文档级范围，不伪造单元级精度。
- 输出每项的旧证据、新提交观察、影响原因、建议复核动作及覆盖限制。结果分为“必须复核”“可能受影响”“尚不能判定”；只有覆盖完整且无变化链的部分才可说明“本次未发现影响”，不承诺线上行为不变。
- 新增或删除组件、跨模块消费者、身份拆分/合并都进入复核队列。重命名识别仅作候选提示，由维护者显式更新 `identity_history` 与证据后才改变身份。

### 2.4 与既有工作流衔接

- 扩展 `preview-upgrade` 增加显式全项目模式；旧的单模块参数及默认 JSON 字段保持兼容。全项目结果使用独立的输出 schema，不修改 `c2kb-file/1`、旧 `0.8.3`、基础 registry、检索单元元数据 schema 或已发布清单格式。单元正文的聚合规则与身份变化须单独回归。
- 预览是只读的审阅材料。确认影响后仍走现有“修订事实与正文 → `impact` → `confirm-claims` → `prepare` → 批准 → 新发布 → 审计”流程；不得自动批准、改写结论、发布或激活。
- 关系缺失、证据无法重建、变更路径无法归属、变化涉及外部依赖或 Adapter 能力不足时，给出**模块级或全项目复核建议**和具体原因。不能用空影响列表暗示可跳过复核。

## 3. 实施顺序与验收

| 阶段 | 实现与文档 | 必须通过的验收 |
| --- | --- | --- |
| A. 索引结构基线 | 冻结公开模块的生成单元、词法与外部检索结果；记录限定拆分、泛标题、术语表及锚点问题 | 至少一条真实生成链被检查；区分结构风险和模型回答错误；不把手写夹具当成生成器证明 |
| B. 最小产物修复 | 保留主题上下文、答案限定和术语缺口报告；修复锚点；制定快照导入契约 | 固定案例在有限 `top-k` 命中目标单元时可取得必要条件和未知；术语缺口显式；旧单元删除与失败保留旧快照的模拟通过 |
| C. 差异与输出契约 | 定义旧/新提交、路径与证据状态、覆盖级别、影响项、降级原因；冻结兼容边界 | 同输入输出稳定；旧 `preview-upgrade` 调用结果不变；预览前后项目目录与 Git 状态均不变 |
| D. 证据和反向影响 | 比较 Git 对象，复用证据快照与 Adapter 声明，定位事实、正文、主题、单元和跨模块消费者 | 证据变化、删文件、偏移、新文件及无关系路径均被报告；移动不自动成为 `verified`；无关系模块明确降级 |
| E. 检索与发布回归 | 用两个固定提交的公开样本做升级演练，复核受影响内容与检索定位 | 改变答案后可召回新条件与未知；无关问题不产生错误出处；业务受众不泄露研发证据；旧项目仍可检查、发布和审计 |
| F. 候选发布 | 文档、兼容说明、变更记录、Release Notes 与 CI | 发布门槛全部通过，PR 合入受保护 `main` 后创建不可移动的 `v0.8.0` 标签和 Release |

阶段 A–B 先确保生成单元适于索引，再由 C–D 贯通一个“旧证据失效”的最小案例。开发期只运行相关测试；公共 CLI、协议兼容、发布审计或受众规则发生变化时跑完整回归。候选冻结时做一次全量本地检查和 Python 3.9–3.13 CI，不以反复跑同一套测试代替问题定位。

## 4. 有意义的回归场景

回归按失效机制选案例，不按题量凑数。至少包含：

1. **条件与答案成组召回**：从公开源码生成含权限、例外和未知的业务单元，用词法基线与一份实际运行的外部 FTS、向量或混合检索结果，在同一语料、同一 `top-k` 下检查目标单元是否带齐必要限定；单独命中“回答边界”不能算答案覆盖。
2. **索引覆盖与替换**：根级术语表在覆盖报告中有明确缺口和原文位置，泛标题带上下文、跨节锚点可达；两版清单模拟标题变更、主题删除、受众迁移，验证旧 ID 删除和失败保留旧快照。
3. **答案确实变化**：公开双提交样本中一条分支条件改变。预览命中固定证据、事实、两版正文和检索主题；维护者修订后，检索评测能找到新条件，旧说法不再进入目标单元。
4. **只有定位变化**：前面插入代码或移动文件，但相关行为未变。旧锚点必须要求重定位复核，不能静默保持 `verified`，也不能仅凭行号变化宣称业务事实改变。
5. **图谱不完整**：新增入口或未关联文件、`candidate/unresolved` 边、跨模块消费者。预览明确给出未覆盖范围或降级建议，不能返回空影响并放行。
6. **无关变化与兼容**：有完整覆盖的无关文件不触发错误的事实复核；旧单模块预览输出、旧协议项目、未启用关系/检索扩展的项目均保持可用，且能力上限如实显示。

使用合成夹具验证确定性边界，再用一份许可明确、固定两个提交的独立公开样本检查真实链路。外部检索记录实现/模型版本、索引字段、分词或嵌入配置、语料摘要与原始排名；手工填写结果只能验证导入格式，不能充当检索实验。无法复现该外部运行时，应明确该门槛未完成，不以 lexical-v1 冒称 FTS。

检索回归只证明**证据能够被定位**；模型生成的最终答案、业务政策和线上运行结果不在本版验收结论内。

## 5. 发布门槛与版本边界

- `check`、关系审计、检索评测、发布审计和公开内容扫描通过；新增公开样本记录来源、许可证及固定提交，不包含使用方私有信息。
- 独立审查指出的限定拆分、泛标题、术语表覆盖、内部锚点和旧单元清理得到修复或明确的受限处理；不得以“文件可被向量化”替代有限 `top-k` 下的证据完整性检查。
- 全项目预览能解释每条进入影响计划的路径及降级原因；至少一个改变业务答案的案例和一个图谱缺口案例由独立复核确认。不能以扫描候选数或测试数量代替知识质量。
- 新旧协议项目的现有检查、准备、发布和审计流程保持；若实现必须修改文件协议或公共 JSON 默认行为，应先另列兼容设计与迁移方案，不借 0.8 版本号直接改变它们。
- 按[公开版本发布流程](release-process.md)在 PR 中审查文档与 Release Notes，完成 Python 3.9–3.13 CI、安装和快速开始复核，再创建标签与 GitHub Release。`v0.7.0` 标签及发布物保持原样。

## 6. 本版不做与后续衔接

0.8 **不执行自动增量重建**，不自动更新事实/正文、审批或发布；不开发生产向量库插件或通用语义去重，不承诺通用重命名、任意语言的语义关系识别，也不接入生产机器人。公开 `c2kb-file/1` 与旧 `0.8.3` 是文件协议兼容标识，不是本版工程号或使用方知识库版本。

通过 0.8 的影响计划与降级边界后，再规划受控增量执行、与同一提交全量重建对账；稳定 CLI/JSON、Adapter 与第三方集成契约仍由 1.0 发布门槛决定。本计划不预设后续版本号或日期，也不授权任何使用方知识库升级。
