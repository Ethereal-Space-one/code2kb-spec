# 0.4.0 检索验收与 0.5.0 启动计划

> 状态：执行中。独立公开样本与开发集基线见[执行记录](0.4.0-检索验收执行记录.md)；不可回答题暴露了基线缺陷，0.4.0 尚未通过验收、合入或发布。本文不把合成夹具成绩写成真实检索质量。样本与题目均须独立于任何使用方的私有知识库。

## 1. 本轮要完成什么

1. 为 0.4.0 建立**可复核的小型真实语义问题集**，验证检索单元能否找到正确证据、保留未知边界并隔离受众。
2. 把开发、集成、合入和发布的回归节点分开，避免每次编辑都执行全套测试。
3. 0.4.0 验收后，启动 0.5.0 的最小事实关系模型设计；此时不启动多语言 Adapter 的大规模实现。

## 2. 样本来源与公开边界

- 选一个许可允许公开再分发的独立示例工程，固定源码提交、许可证与引用位置。优先选择同时有用户文档、实际错误分支和权限边界的项目；不能只选 API happy path。
- 从该提交生成可公开的知识源和检索单元。题目由文档、代码行为、错误条件与真实使用场景推导，再经人工逐题核对；不使用本地母项目、客户日志、内部问答或凭据。
- 如果公开许可证不允许再分发材料，则只保留允许公开的出处元数据；不能把限制内容改写后当作自有夹具。
- 现有带 `demoNN` 唯一标记的 120 单元／96 题只做规模和确定性检查，**不计入质量验收**。

## 3. 每道题必须有的审核记录

问题集按**不同失效机制**选题，不按题数凑配额。每题先写审核记录，复核通过后才进入冻结问题集：

| 字段 | 必须说明 |
| --- | --- |
| 用户问法 | 自然、简短；不出现 `module_id`、单元 ID、源码类名或只在答案中出现的唯一标记 |
| 场景与类别 | 正常操作、失败/例外、限制/权限、未知/不可回答、跨模块同名或条件变化；说明此题能检出什么错误 |
| 证据 | 固定提交、仓库相对路径、具体段落或行号，以及对应的已发布检索单元 |
| 正确判断 | 应命中的模块/单元、必须保留的条件和未知、不能说出的结论；不可回答题明确应拒答的原因 |
| 干扰项 | 指明一个最容易误召回的相近单元或错误答案，说明两者差别 |
| 公开许可 | 材料许可、题目与答案可公开的依据 |
| 审核结果 | 人工核对人、日期和结论；证据变化时重新审核 |

同一主题的改写问法只算一个覆盖点，全部放在同一开发集或保留集，不能一边训练调参、一边充当独立验收。没有固定证据、只换几个字、没有独立干扰项或无法解释测试价值的题目删除。

## 4. 问题集结构与必要改动

先做覆盖矩阵，再写题目：至少覆盖真实操作、失败条件、未知边界、权限限制、同名主题、跨模块路由和来源版本。每类只保留能触发**不同错误**的代表题；某类确实不存在时登记“不适用”及证据，不造场景。

当前 `retrieval-evaluate` 要求每题提供预期模块或单元，无法表达“正确结果是没有可支持答案”；`required_phrases` 检查的是**被检索文本**，不是机器人生成的回答。验收前必须明确补充不可回答题的结构化判定与测试，或单独建立拒答评测器；不能把无答案题伪装成“找到一个未知单元”便称已验证拒答。检索验收报告也不得宣称生成回答已正确。

冻结时保留两组：开发集用于定位问题；保留集在生成规则和排名权重确定后才运行。按主题与失效机制分组，避免同一答案的不同问法跨组泄漏。题目与金标准随固定提交、语料摘要和评测器版本一起锁定。

## 5. 0.4.0 验收门槛

1. 每题审核记录完整；证据可从固定提交重建，许可和公开内容扫描通过。
2. 受众泄漏、错误发布版本、错误出处、已知误答、遗漏关键未知边界等安全和事实边界问题须为 **0**；任何一例都阻断“检索就绪”。
3. 开发集与保留集分别报告 module/unit recall@k、MRR、必要条件、未知保留、重复召回、无答案表现及失败明细。普通召回统计阈值在看到基线后冻结，并记录选择理由；不事后降低阈值迎合结果。
4. 与当前 `lexical-v1` 和未切主题的基线比较。新增检索版若只在合成题上提升、真实语义题退步，不通过。
5. 人工抽查所有失败和边界题；修复后重跑受影响题与保留集。保留集若被用于调参，该组作废并重新选题。

这里的“通过”只表示**离线检索证据定位**达到本计划门槛，不表示生产机器人最终回答、线上权限或业务政策已验证。

## 6. 分层回归节点

| 节点 | 运行范围 | 触发条件 |
| --- | --- | --- |
| 每次编辑 | 受影响模块单测、相关夹具、差异和格式检查 | 所有代码改动；文档改动只跑链接与公开内容扫描 |
| 能力接通 | 该链路的集成测试、故意失败用例及固定检索题 | 单元生成、评测、审计、事实模型或 Adapter 任一能力贯通 |
| 高影响改动 | 立即跑全量单测与一致性夹具 | 文件协议、公共事实身份、发布/审计逻辑、受众隔离、CLI 兼容性变化 |
| 候选冻结 | 一次完整本地回归与独立保留集；PR 上跑 Python 3.9–3.13 CI | 内容停止修改，准备合入 |
| Release | 核对标签、提交与通过 CI 的构建物相同 | 同一提交不重复执行等价全套；有任何内容变化则重新候选冻结 |

当前 CI 对每次 PR 更新都运行全套。开发中先在本地积累小提交，形成可审阅的 PR 候选后再推送；不为省时绕过合入前的 CI。若以后要拆分快速 CI 与全量 CI，须先确认分支保护仍要求全量结果。

## 7. 执行顺序与交付物

1. **协议和题目设计**：选独立样本，形成许可与固定提交记录、覆盖矩阵、逐题审核表；先评审题目质量，不急于扩大数量。
2. **补齐评测表达能力**：支持真正的不可回答判定，明确检索评测与生成回答评测的边界；只跑评测模块的定向测试。
3. **冻结开发集、保留集和基线**：运行一次当前实现，记录失败、差异和预先确定的门槛；只修证据支持的问题。
4. **0.4.0 候选收口**：完成独立保留集、公开扫描、全套本地回归、PR CI；根据结果决定合入和发布，不直接用合成规模成绩放行。
5. **0.5.0 设计启动**：先产出入口—接口—方法—事实—检索主题的最小关系契约、稳定 ID 与证据重建夹具；待 0.4.0 检索门槛通过后扩大自动化实现。

若独立样本无法合法公开，先停在本地验证与选材，不把私有案例或脱敏不足的摘录提交到开源仓库。
