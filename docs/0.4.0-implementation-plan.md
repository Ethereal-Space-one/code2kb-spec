# Code2KB Spec 0.4.0 实施计划

> 状态：本地候选实现；标签与 GitHub Release 尚未执行。本文仅规划开源工程 `0.4.0`，不改写已经公开的文件协议兼容标识 `0.8.3`，也不引用任何使用方知识库的版本号。

## 1. 版本目标

0.4.0 先验证 Code2KB 产物是否适合知识检索，再扩大运行编排、语言范围和增量能力。

本版完成后，应能从一个已经通过 Code2KB 审核的发布快照，确定性生成按受众隔离的单主题检索单元，使用固定问题集验证召回、事实、未知边界和出处，并把检索结果绑定到基础发布版本。

### 1.1 成功定义

1. 同一输入重复生成相同检索单元 ID、正文摘要、清单和评测结果。
2. 一个检索单元围绕一个可回答主题，回答需要的条件、结论、例外和未知边界不会被拆散。
3. 业务问题默认只检索业务单元；研发问题可以检索研发单元及其复用的业务结论。
4. 真实问题集能输出 Top-k 命中、必要事实、未知保留、重复召回、受众泄漏和出处正确性结果。
5. 检索评测失败时不能标记为“检索就绪”。
6. 现有 0.3.x / 知识规范 0.8.3 项目仍可检查、审核、发布和审计。
7. 0.4.0 不依赖特定机器人、向量数据库、云模型或外部服务才能完成基础回归。

## 2. 范围边界

### 2.1 本版实现

- 检索单元实验契约；
- 业务检索版和研发检索版；
- 轻量路由索引；
- 确定性检索生成与审计；
- 内置无外部依赖的检索基线；
- 外部检索结果导入协议；
- 检索评测 fixture、报告和门禁；
- 精简正文 profile；
- Agent Toolkit 提示分层；
- 与现有发布快照兼容的检索扩展清单；
- 公开夹具、脱敏规模统计和回归报告。

### 2.2 本版不实现

- `run_id`、持久运行账本和跨进程恢复；
- Claude Code、Codex Host Adapter；
- 全项目自动编排或模块并行写入；
- 确定性全仓组件图；
- 规范化事实数据库；
- 多语言官方 Adapter 扩张；
- 源码增量更新；
- MCP Server；
- 特定机器人、消息平台或向量数据库的生产部署自动化；
- 模型裁判或在线模型依赖；
- 直接升级知识规范 0.8.3。

## 3. 兼容设计决策

### 3.1 保持知识规范 0.8.3

当前公开文件协议的版本清单 `registry_schema_version: 2.0` 严格只允许 `business` 和 `engineering` 两个视图；当前版本指针中的发布目录路径是 `business_path` 与 `engineering_path`。0.4.0 不直接增加第三个 `views.retrieval` 字段，也不改写现有指针。

检索产物作为 0.4.0 的实验扩展，与基础发布绑定：

```text
发布/
├── 业务版/
├── 研发版/
├── 版本清单/<release_id>.json
├── 当前版本.json
├── 检索版/
│   ├── 业务/
│   └── 研发/
├── 检索清单/<release_id>.json
└── 当前检索版本.json
```

`检索清单` 必须记录基础 `release_id`、基础 registry 路径与 SHA-256。基础发布发生变化后，旧检索清单立即失效。0.3.x 工具仍能审计业务版和研发版；0.4.x 另外审计检索扩展。

### 3.2 检索单元使用 Markdown

首版使用“一单元一 Markdown 文件”，原因是：

- 可直接交给文件索引器和常见 RAG 工具；
- 能被 Git 审阅和逐文件摘要审计；
- 复用现有 UTF-8 与 front matter 解析方式；
- 不需要同时维护 JSONL 和 Markdown 两套内容。

检索清单提供机器可读目录。后续消费者需要 JSONL 时，由清单和 Markdown 确定性导出，不把 JSONL 设为第二事实源。

### 3.3 检索单元不人工维护

检索单元是发布派生产物。人和 Agent 修改知识源、事实或正文；工具重新生成检索单元。禁止直接编辑 `发布/检索版` 修复答案。

### 3.4 精简 profile 不增加新文件类型

0.4.0 继续使用知识规范 0.8.3 已有文件名：

| 内容组 | 默认承载文件 | 合并策略 |
| --- | --- | --- |
| 概览与范围 | `模块概览.md` | 把必要范围、入口和角色写入概览；`功能与范围.md` 可省略 |
| 流程与规则 | `规则与限制.md` | 把必要流程、失败、权限、例外和未知写在同一主题附近；`业务流程.md` 可省略 |
| 用户问答 | `常见问答.md` | 保留真实问法和直接答案 |
| 技术链路 | `技术实现.md` | 业务到入口、接口、方法和证据导航 |
| 接口与数据 | `接口与调用.md` | 接口、校验、数据副作用和配置 |
| 复杂方法 | `方法与源码.md` | 仅在独立检索价值足够时生成 |
| 业务意图 | `业务意图.md` | 继续按证据可选生成 |

旧五类业务正文和三类研发正文继续作为 `full` profile；新项目可选 `compact` profile。两种 profile 使用同一检索单元契约和评测门禁。

## 4. 检索单元契约

### 4.1 文件身份

建议路径：

```text
发布/检索版/<受众>/<业务域>/<模块>/<unit_id>.md
```

`unit_id` 由受众、`module_id`、来源文档类型、规范化标题和冲突短摘要确定。正文变化只改变内容摘要；标题或来源身份变化可以产生新 ID，重命名识别留到 1.0.0。

### 4.2 Front matter

实验字段建议如下：

```yaml
---
document_type: retrieval_unit
retrieval_schema_version: 0.1
unit_id: ru.business.app.customer.search.faq.current-month-count
module_id: app.customer.search
audience: business
topic: 近30天跟进口径
question_variants: 近30天跟进怎么算,为什么跟进次数对不上
source_documents: 电话销售/客户查询/常见问答.md
source_headings: 问：近30天跟进真的是滚动30天吗
fact_ids: F-08
traceability_level: fact
release_id: example-release
---
```

约束：

- `audience` 只允许 `business`、`engineering`；
- `question_variants` 是检索表达，不承载答案；
- `source_documents` 和 `source_headings` 必填；
- `fact_ids` 在 0.4.0 可以为空，此时 `traceability_level: document`；
- `release_id` 必须与基础发布一致；
- 业务单元继续通过业务技术词扫描；
- 未知边界存在时必须留在正文中，不能只写入元数据。

### 4.3 正文结构

```markdown
# <主题>

## 适用条件

## 结论

## 例外与失败

## 仍不能确定

## 出处
```

没有证据的章节省略。生成器不得为了填满模板制造条件、例外或未知。

### 4.4 来源选择

0.4.0 从已审核发布正文生成单元，不重新解释源码：

1. `常见问答.md` 中每个问题作为优先业务主题；
2. `规则与限制.md` 中没有被问答覆盖的独立标题作为补充主题；
3. `模块概览.md` 提供模块定位、入口、角色和整体范围主题；
4. full profile 下的 `功能与范围.md`、`业务流程.md` 只补充未覆盖主题；
5. 研发单元按 `技术实现.md`、`接口与调用.md`、可选 `方法与源码.md` 的标题生成，并复用必要业务边界；
6. `业务意图.md` 只在基础发布已包含时生成对应业务单元；
7. 导航、索引、发布信息和事实编号对照不直接成为答案单元。

生成内容优先复用原文段落；需要重排时只做确定性章节组合。0.4.0 不用模型自由改写已审核结论。

### 4.5 重复控制

生成器分三层处理：

1. 完全相同规范化正文：确定性合并，保留全部出处；
2. 同模块、同受众、标题和关键词高度相似：标记 `duplicate_candidate`，进入报告；
3. 语义近似但无法确定等价：不自动合并，由评测暴露重复召回。

0.4.0 不使用向量相似度自动删除知识，也不让模型在发布过程中静默合并结论。

### 4.6 检索元数据生成

现有发布清单的 `business_topics`、`business_unknowns`、`business_keywords` 及研发对应字段继续保留，避免破坏 0.8.3。0.4.0 增加自动候选路径：

- topics 来自检索单元主题；
- keywords 来自模块名、可靠 aliases、问题表达和主题标题，经过停用词、同义重复和业务/研发受众过滤；
- unknowns 来自检索单元的“仍不能确定”正文；
- 自动结果必须能回链到检索单元，禁止根据词频生成正文不存在的主题；
- `prepare` 的显式参数继续可用，并优先于自动候选；
- 稳定后增加 `prepare --auto-retrieval-metadata`，省略的字段由候选补齐，生成结果仍写入现有必填字段。

这样可以减少手工重复输入，同时不改变 0.8.3 发布清单结构。

## 5. 检索扩展清单

建议新增 `retrieval_manifest_schema_version: 0.1`，字段至少包括：

- `release_id`；
- `base_registry_path`；
- `base_registry_sha256`；
- `generated_by`；
- `generated_at`；
- `profile`；
- `retrieval_schema_version`；
- `views.business.path/files`；
- `views.engineering.path/files`；
- `evaluation_suite` 与摘要；
- `evaluation_report` 与摘要；
- `retriever_id`；
- `gate_status`；
- 单元数、模块数、document/fact 两种追溯等级计数。

当前检索指针必须同时绑定检索清单摘要和基础 registry 摘要。`audit-retrieval` 核对：

- 基础发布仍通过原 `audit-release`；
- 基础 release ID 和 registry 摘要一致；
- 检索目录无增删改；
- 业务与研发目录不相交；
- 单元元数据、受众和路径一致；
- 评测报告绑定当前单元摘要；
- 指针、清单、目录和报告四方一致。

## 6. 检索评测设计

### 6.1 Fixture

建议使用 JSON：

```json
{
  "schema_version": "0.1",
  "suite_id": "minimal-business-v1",
  "audience": "business",
  "cases": [
    {
      "case_id": "customer-search-current-month",
      "query": "近30天跟进真的是滚动30天吗？",
      "expected_module_ids": ["app.customer.search"],
      "expected_unit_ids": ["ru.business.app.customer.search.faq.current-month-count"],
      "required_phrases": ["当前账期", "不是滚动"],
      "required_unknown_phrases": ["业务口径"],
      "forbidden_phrases": ["已经线上验证"],
      "top_k": 3
    }
  ]
}
```

真实 fixture 不依赖某个公司模块；公开仓库使用许可明确的小型通用示例。

### 6.2 内置检索器

提供 `lexical-v1` 作为确定性基线：

- 中文字符 unigram/bigram；
- 英文和数字按规范化 token；
- BM25 或等价确定性词法评分；
- `module_id`、aliases、topic、question variants 和正文使用明确固定权重；
- 分数相同时按 `unit_id` 排序；
- 不依赖网络、模型或第三方数据库。

该检索器用于回归和比较，不宣称代表所有生产 RAG 系统。

### 6.3 外部结果导入

定义外部结果 JSON，使向量数据库或其它检索器可以提交：

- `suite_id`、`retriever_id`、版本与配置摘要；
- 每个 `case_id` 的有序 `unit_id` 和分数；
- 执行时间与语料摘要。

评测器只核结果，不获取凭据、不调用外部服务。

### 6.4 指标

必须输出：

- module recall@k；
- unit recall@k；
- MRR；
- required phrase coverage；
- required unknown coverage；
- forbidden phrase hit；
- audience leakage；
- duplicate hit ratio；
- source/release correctness；
- 无结果和错误结果明细。

### 6.5 门槛策略

不在编码前臆定真实项目阈值：

1. 固定公开 fixture 使用精确期望并作为硬门禁；
2. 脱敏规模库先生成基线报告；
3. 根据基线冻结 0.4.0 RC 的默认阈值；
4. 项目可以采用更严格阈值，但不能关闭受众泄漏、错误 release 或清单摘要检查；
5. 阈值和检索器身份进入评测报告与检索清单。

## 7. CLI 设计

沿用现有单层 action 风格，新增：

```text
code2kb retrieval-build --project-root ... --release-id ... --profile full|compact
code2kb retrieval-evaluate --project-root ... --release-id ... --suite ... --retriever lexical-v1
code2kb retrieval-evaluate --project-root ... --release-id ... --suite ... --results external-results.json
code2kb retrieval-audit --project-root ... --release-id ...
```

0.4.0 不引入 0.6.0 的统一运行状态机。新增命令继续使用现有退出码和错误输出约定；结构化 JSON 响应统一留到 0.6.0。

发布集成分两步：

1. 首先允许对已有基础发布执行 `retrieval-build/evaluate/audit`；
2. 稳定后为 `publish` 增加显式 `--with-retrieval --retrieval-suite ...`，在临时目录生成并评测，全部通过后再原子替换发布快照。

默认 `publish` 行为在 0.4.0 中保持兼容；未显式启用检索扩展时不新增目录和指针。

## 8. Agent Toolkit 简化

### 8.1 目标结构

```text
skills/extract-app-knowledge/
├── SKILL.md
├── contracts/
│   ├── core.md
│   ├── inventory.md
│   ├── extract.md
│   ├── author.md
│   ├── evaluate.md
│   └── release.md
└── extensions/
    ├── business-intent.md
    ├── runtime-evidence.md
    ├── policy-review.md
    ├── semantic-quality.md
    └── migration.md
```

### 8.2 分层规则

- `core.md` 只保留固定提交、证据等级、未知、受众隔离、批准与源码只读等不可变规则；
- 每次任务只加载一个 task contract；
- extensions 仅在配置或任务明确需要时加载；
- 文件名、front matter、清单字段、摘要和目录由工具或模板渲染器负责；
- Prompt 不重复 CLI 帮助和完整 Schema；只引用稳定契约入口；
- 迁移前后用固定 prompt fixture 比较上下文行数、输出合规率和遗漏率。

### 8.3 兼容方式

现有 `SKILL.md` 继续作为入口；原 `references/` 在一个版本内保留兼容链接。0.4.0 不要求第三方宿主立即改路径。

## 10. 分阶段实施

### 阶段 A：冻结基线

交付：

- 现有 119 项测试结果；
- 公开 minimal project 的文档、索引和主题统计；
- 一份公开合成规模库的数量与重复统计；真实项目统计在明确允许后单独补充；
- 现有发布、审计和指针行为快照。

门禁：没有改动现有行为；基线可在 CI 重复生成。

### 阶段 B：契约与固定夹具

交付：

- 检索单元、检索清单、当前检索指针、评测 fixture 和外部结果 Schema；
- 有效、无效和安全边界夹具；
- 稳定 ID 与摘要算法说明。

门禁：Schema、路径安全、重复字段、未知字段、摘要绑定和受众规则全部有测试。

### 阶段 C：检索生成与审计

交付：

- 章节解析、FAQ 解析、来源选择、确定性去重和单元渲染；
- `retrieval-build`；
- `retrieval-audit`；
- full profile 兼容生成。

门禁：重复生成摘要一致；人为增删改单元后审计失败；业务技术词和受众串线被拒绝。

### 阶段 D：检索评测

交付：

- `lexical-v1`；
- 外部结果导入；
- 指标计算、JSON/Markdown 报告；
- `retrieval-evaluate`；
- 固定公开问题集。

门禁：故意制造错模块、漏未知、研发泄漏、错误 release、重复命中和无结果时均能失败或准确报告。

### 阶段 E：精简正文与提示分层

交付：

- compact profile；
- full 与 compact 主题覆盖对照器；
- core/task/extensions 提示结构；
- 自动关键词、主题和未知摘要候选；
- 现有 Skill 路径兼容层。

门禁：compact 不丢公开 fixture 的可回答主题；提示上下文减少且结构合规率不下降。

### 阶段 F：发布集成与 RC

交付：

- `publish --with-retrieval`；
- 基础 release、检索清单、评测报告和指针的原子发布；
- 0.3.x 兼容报告；
- 默认阈值冻结；
- README、使用指南、CHANGELOG、版本号和公开审计报告。

门禁：旧项目不启用扩展时结果不变；启用后基础和检索审计同时通过；完整回归、公开内容扫描和一致性检查通过。

## 11. 建议的 Pull Request 划分

1. **PR-1 基线与契约**：只增加统计、Schema、夹具和文档。
2. **PR-2 检索生成**：model、build、audit 和单元测试。
3. **PR-3 检索评测**：内置检索器、外部结果协议、指标和固定问题集。
