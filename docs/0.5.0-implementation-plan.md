# Code2KB Spec 0.5.0 实施计划

> 状态：实施完成，作为 `v0.5.0` 发布依据。基线为 `v0.4.0`；本计划只针对开源工程，不包含任何使用方项目、源码或知识库。工程版本 `0.5.0` 与知识文件协议版本独立，关系能力作为可选独立扩展实现。

## 1. 目标与验收对象

0.5.0 要让一条可检索结论能够回溯到**已复核的结构化事实和固定源码证据**，并让来源变化时的影响范围可计算。关系模型服务于取证、覆盖对账和检索出处；它不判断业务政策，也不替下游模型决定如何回答。

完成的标志是：在公开固定样本中，能从一个检索主题追到事实、方法、接口和入口，重新从固定提交取得证据；缺失或冲突的边明确标为待核查，不能被工具补成“已证实”。只检索到相关单元仍不等于模型答复正确。

## 2. 已有基础与实际缺口

| 现有能力 | 0.5 要补的部分 |
| --- | --- |
| 功能大纲已有 `entry_id`；结构化规格已有 `fact_id`、`api_id`、`method_id` 及入口到接口、接口到方法的表 | 统一局部 ID 的命名空间和跨表关系；补充方法到事实、事实到检索主题的显式关系与反向覆盖报告 |
| `source_revisions` 和 `仓库ID:路径:行号` 可检查固定提交中的文件与行号 | 固定提交、路径、行号、引用片段摘要和 Git blob identity 一起绑定；重建时检查引用内容，而不只检查行号存在 |
| 0.4 的检索单元有 `fact_ids`、`traceability_level`，检索清单绑定基础发布摘要 | 目前正文未含事实编号时只能得到文档级追溯；建立经复核的主题到事实映射，不从相似文字猜测事实关系 |
| `impact`、`confirm-claims` 已覆盖部分事实到正文的变化流程 | 将新关系纳入影响预览与覆盖对账，同时保持现有语义复核步骤；不让关系图自动批准结论 |
| 现有 UniApp 页面入口盘点适配器 | 增加首批 UniApp/TypeScript 与 Java 的确定性候选发现，但必须说明能力边界、保留未归类项 |

## 3. 范围与设计约束

### 3.1 最小关系契约

节点类型：`entry`、`interface`、`method`、`event`、`task`、`config`、`field`、`fact`、`topic`。后四类只在样本确有证据、且会影响结论或覆盖时登记；不为填图造节点。边至少支持 `entry → interface`、`interface → method`、`method → fact`、`fact → topic`，以及任务/事件触发的方法、配置/字段影响的事实。每条边记录来源、证据、状态和复核记录；关系可为 `verified`、`candidate` 或 `unresolved`。`candidate` 不可当作已证实路径展示。

复用现有 `entry_id`、`api_id`、`method_id`、`fact_id` 和 0.4 `unit_id`。事实的全局引用使用 `module_id#fact_id`；`topic_id` 是跨正文标题变动保持稳定的主题身份，另用映射关联当次发布的 `unit_id`。**不要把标题、文件路径、行号或内容摘要当作长期身份**：这些是可变化的定位属性。已有 ID 不因加入关系清单而重新编号。重命名保持身份，拆分/合并创建新身份并在 `identity_history` 记录旧 ID、新 ID 与原因；语义变成另一事实时也创建新身份，不悄悄沿用旧 ID。

每模块的显式关系映射、身份变更史和边复核状态放在知识源侧的**可编辑权威输入**中；结构化规格仍是事实结论源。发布时从这些已复核输入确定性生成独立、版本化的关系清单，冻结事实、证据与边的必要快照，并绑定基础 registry 和对应检索清单的摘要。关系清单是派生索引，不是第二套事实正文；旧发布的审计只读当次冻结产物，不读取后来变化的工作稿。管理侧可查证据链，业务检索输出仍按受众隔离，不输出内部方法、配置键、源码路径或片段。

关系映射、规范化事实、证据和身份历史的摘要须进入 `impact` 与候选审核快照；仅改变边的端点、状态或证据也会使旧复核失效。扩展采用独立清单，不直接给现有严格字段集合的检索单元、registry 2.0 或当前版本指针加字段。旧项目没有关系清单时仍可使用文档级出处，报告为 `document`，不得冒充事实级追溯。

### 3.2 证据重建

每条代码证据保存仓库逻辑 ID、完整固定提交、仓库相对路径、行号或行段、引用片段 SHA-256、Git blob identity 和证据等级。工具用 `git show <commit>:<path>` 及 Git 对象信息重新解析，核对路径安全、对象类型、行段和片段摘要；不读取未提交工作区作为正式证据。源码移动或行号变化时先报告断链，再由复核者建立新定位；相似文本搜索只能提出候选，不能自动替换锚点。

固定旧提交的证据不会因工作区或后续提交发生变化而失效。显式切换取证提交时，旧路径/行号/片段摘要不能沿用为新提交的 `verified`；工具应在新配置的完整校验之前读取旧、新证据记录，预览受影响事实与主题，再由复核者迁移定位并运行现有校验。这是最小升级路径，不实现通用增量更新。

`CODE_VERIFIED` 只证明该快照中的代码与调用结构。动态配置值、服务部署配对、运行结果、业务动机和推断依旧各守原证据等级。RAG、全文或向量检索可以帮助找材料，不能成为正式证据。

### 3.3 候选发现与人工/Agent 归类

首批适配器只发现确定性候选：UniApp 页面/组件入口与 TypeScript 调用点；Java 路由、方法和明确的调用表达式。解析不清的动态路由、依赖注入、反射、网关改写、跨仓调用保留 `unresolved`。候选报告带发现规则、源码锚点和能力边界；由复核者或 Agent 根据证据归类到模块与事实，归类结果再接受确定性校验。适配器不能直接产出业务事实或“全仓覆盖”声明。先冻结解析器、依赖与安装方式，保证 Python 3.9–3.13 的 CI 可重复运行。

旧规格中的“调用匹配”状态要显式迁移：`疑似匹配` 只能成为 `candidate`，`未匹配/外部依赖` 只能成为 `unresolved`；`已匹配` 还须核对两侧固定证据与复核记录，才可成为 `verified`。目录中存在 ID、路径和行号，不足以证明边已匹配。任务、事件、配置和字段关系也逐类定义状态来源，不套用接口匹配规则。

0.5 的 TypeScript/Java 是**首批参考分析范围**，不是全语言平台。统一 Adapter SDK、L1/L2/L3 能力分级及更多语言留给 0.7。为避免和既有 UniApp 页面盘点器重复，先复用其页面清单，再增加调用关系候选。

### 3.4 事实驱动正文的渐进方式

结构化规格的已复核事实是本版关系模型中的权威结论源。先在一个公开样本模块中提供条件、结论、例外、未知边界的规范化事实记录，从同一事实生成业务版、研发版与检索版的**事实结论段和出处**，并验证三处条件与未知边界一致。面向读者的解释文字仍可编辑，但若新增可核结论，必须关联事实并走 `impact → confirm-claims`。不在 0.5 强制把所有旧正文改写成模板文本，也不自动用模型重写发布正文。

## 4. 实施顺序

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| A. 契约与身份 | 可编辑映射输入与派生清单的独立契约、审核摘要范围、稳定 ID/拆并规则；扩展公开源码格式扫描 | 旧 ID 原样保留；同输入输出同摘要；映射改动使复核失效；每种新增源码格式的合成敏感标记均被扫描拒绝 |
| B. 证据重建 | 固定提交证据记录器、验证器及跨提交影响预览 | 旧提交在工作区变化后仍可重建；切换新提交不能沿用旧定位为 `verified`；旧、新记录可预览影响再迁移 |
| C. 最小关系与覆盖 | 从现有大纲/规格生成边和反向索引；方法到事实、事实到主题由显式映射给出；覆盖差异报告 | 一个完整链条可双向追踪；旧规格合法但调用仅疑似匹配时不得升为 `verified`；未归类入口、孤立事实、文档级主题分别报告 |
| D. 首批分析适配 | UniApp/TypeScript、Java 的候选扫描与能力说明；公开混合语言夹具 | 静态可见路径准确发现；动态/跨仓关系为候选或未解；与现有页面入口清单对账 |
| E. 检索与影响集成 | 独立关系扩展审计、主题映射、影响预览；一个公开模块从同一事实生成双版与检索版的事实结论段 | 事实或映射变化能列出受影响主题与单元；工作稿变化不改变旧发布审计；业务查询不泄漏技术证据；三版条件与未知边界一致，0.4 默认行为不变 |
| F. 候选冻结与发布 | 使用文档、独立复核记录、变更日志、兼容报告、Release 材料 | 固定公开样本通过下文门禁，Python 3.9–3.13 CI 与受保护分支合入通过 |

阶段 A–C 先贯通一条小链路，再做适配器扩展。不要在关系、证据和身份尚未稳定时批量生成大纲或知识正文。

## 5. 有意义的回归与发布门槛

公开夹具按**失效机制**选取，不按题数凑覆盖：正常链、旧协议合法但调用仅“疑似匹配”的链、同名跨模块、动态未知、跨提交证据变化、仅修改映射、旧发布兼容、业务/研发受众边界各至少有一个能触发对应检查的场景。以独立、许可允许再分发的样本交叉核对一条真实链路；合成样本只验证规则，不宣称通用取证准确率。新增 `.java/.ts/.tsx/.vue/.js` 夹具前，先扩展公开内容扫描及其故意失败用例；许可证与出处一并登记。不得引入任何私有项目文件或题目。关系夹具必须接入可执行 conformance runner 和 CI；只登记覆盖编号不算通过。

开发期每次编辑仅跑受影响的契约、证据或适配器测试；能力首次贯通时跑对应集成夹具。稳定 ID、文件协议、发布/审计或受众规则有变化时立即跑全量兼容回归。候选冻结时一次完成全量本地回归、公开内容扫描、独立样本复核和 Python 3.9–3.13 PR CI；同一提交发布时只核对标签与通过 CI 的提交一致，不再重复等价全套。失败后只重跑受影响项和最终候选门禁。

0.5.0 必须满足路线图门槛：稳定事实身份、入口与事实覆盖对账、证据从固定提交重建。还要证明错误关系不会静默进入 `verified`，事实变化能够定位受影响检索主题，未知边界与受众限制未丢失。检索评测继续只度量**证据定位**；最终问答组合与拒答另行测试，不把这项能力虚报为 0.5 的成果。

## 6. 明确留给后续版本

- 0.6：跨进程恢复、`run_id` 账本、写入集合、Host Adapter 和全库执行编排。
- 0.7：统一多语言 Adapter SDK、能力等级及更多语言支持。
- 1.0：通用源码增量更新、重命名识别与全量重建对账。
- 不纳入本版：生产机器人接入、向量数据库、模型答复质量门禁、业务政策推断、运行环境真值判断。

## 7. 开工次序

1. 在独立 0.5 开发分支冻结契约、ID 和公开夹具；确认它们不含使用方痕迹。
2. 实现证据重建与最小关系链；用故意损坏的夹具证明门禁真的会失败。
3. 接入两个首批分析适配范围，明确候选与已核证据的分界。
4. 接入检索出处与影响预览，完成兼容回归、独立复核、PR 和发布准备。

本文件是实施依据，不构成发布授权；每阶段产物应在可审阅的提交或 Pull Request 中展示。
