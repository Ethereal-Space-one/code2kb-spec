# 1.0 公开消费契约（待发布）

本页限定 Code2KB Spec 1.0 拟承诺的**最小兼容表面**。当前开发分支仍为 0.8.0，发布前须核对实际版本与下述测试。Code2KB 从固定源码提取业务行为和代码逻辑知识；源码候选、只读升级计划都不能代替复核后的知识正文或发布审批。

## 源码升级只读计划

入口为 `code2kb preview-upgrade --project-root PROJECT --all-modules --repository-id ID --new-commit COMMIT --plan`。可将上次结果的 `plan_sha256` 传入 `--expect-plan-sha256 SHA` 复算核对；输入改变则命令失败。该参数**不是接受、执行或批准计划**。旧 `--module-id` 输出 schema `0.1`、不带 `--plan` 的全项目输出 schema `0.2`，继续维持原行为。

`--plan` 的 JSON schema 为 `1.0`。稳定读取字段如下；消费者须忽略未知额外字段。同一数组中的模块 ID 按字典序去重排列，摘要是小写 64 位十六进制字符串。

| 字段 | 兼容含义 |
| --- | --- |
| `schema_version`, `kind` | 固定为 `1.0`、`source_upgrade_review_plan`；不支持的版本应拒绝消费 |
| `repository_id`, `old_commit`, `proposed_commit` | 计划比较的仓库及完整固定提交 |
| `decision` | `selected_modules` 或 `full_project_review`；后者须复核全项目 |
| `selected_modules` | 需重新解释语义的候选模块 ID；即使非空，也**不授予自动执行或跳过审核的权限** |
| `fallback_reasons` | 回退原因列表；具体原因字符串是诊断信息，消费者应展示原文，不以其枚举值驱动授权 |
| `input_snapshot`, `plan_sha256` | 输入快照与本次计划摘要；摘要只作过期核对，不是签名或内容可信证明 |
| `review_scope_metrics` | 语义复核、基线触及、审核刷新等**不同范围**的计数，不能互相替代或当成人工工时 |
| `execution_gate` | 固定为 `baseline_migration_and_explicit_review_required`；表示仍有迁移和明确审核门槛 |

`input_snapshot` 中稳定可读的子字段为：`knowledge_git_head`（完整提交号或 `null`）、`knowledge_worktree_dirty`（布尔值），以及 `config_sha256`、`source_tree_sha256`、`relations_sha256`、`approval_manifests_sha256`、`runtime_evidence_tree_sha256`（存在输入时为小写 SHA-256；`config_sha256` 在没有文件时可为 `null`）。其他指针摘要供诊断；消费者须把整个 `plan_sha256` 当作不透明比较值，不能只用这些子字段自行重算。

`review_scope_metrics` 中稳定可读的子字段是非负整数 `modules_total`、`semantic_review_modules`、`baseline_touch_modules`、`approval_refresh_modules`。其含义分别为大纲模块总数、建议重新解释业务语义的模块数、需刷新本仓固定提交或关系文件的模块数、需重新审核正文或清单的模块数。其余计数是诊断信息。这四项都不是实际耗时，也不保证基线迁移可自动完成。

`changed_paths`、`must_review_facts`、`affected_topics`、`needs_evidence`、`baseline_migration` 的详细行用于人工诊断；其细分字段、回退原因代码和中文说明不作为 1.0 稳定机器决策接口。特别是 `baseline_migration.status: read_only_proposal_not_applied` 只描述未执行状态。任何消费者都不能凭 `selected_modules` 修改全局配置、重建证据、复用旧批准或启动 `run-create`。

命令成功退出码为 0；参数错误、过期计划或无法验证的输入以非零退出。`--output json` 使用现有 `response_schema_version: 0.1` 信封，稳定区分 `status: completed|failed`；具体诊断文本和非零数值不用于工作流判断。

## 已有文件与候选契约

- 知识文件：新项目默认 `c2kb-file/1`，旧 `0.8.3` 可继续读取、检查和审计；[知识文件说明](knowledge-format.md)与[兼容性说明](compatibility.md)仍是格式依据。工程版本 `1.0.0` 不是知识文件协议编号。
- 检索扩展：仅显式启用时生成，单元 `retrieval_schema_version: 0.1`；消费者按受众读取已审计的当前版本并使用 `(release_id, audience, unit_id)` 为键。[检索扩展契约](retrieval-contract.md)定义完整字段和快照切换。检索命中不代表答案经过运行验证。
- Adapter：候选 schema `0.2` 和 `validation.adapters.sdk.CandidateAdapter` 是当前可用的最小 SDK 表面；L1/L2/L3 只描述候选发现能力，`candidate` 和 `unresolved` 都不能自动升为已验证事实。[Adapter 契约](adapter-contract.md)列出字段与降级语义。默认旧候选 schema `0.1` 不变；CLI 不自动加载第三方项目代码。

## 兼容验证

发布前在 Python 3.9–3.13 CI 中运行完整测试、公开一致性夹具、历史发布审计、检索/关系契约测试、Markdown 链接和公开内容检查；使用干净安装验证 `code2kb --help` 与 `--version`。现有负例核对过期输入与未知路径回退；双模块和 PetClinic 五模块案例核对 1/2、1/5 的语义范围，同时保留 2/2、5/5 的迁移与审核成本。公开案例不构成生产模型回答质量或自动增量执行收益证明。
