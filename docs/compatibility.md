# 兼容性说明

| 工程版本 | 知识规范 | 兼容结论 |
| --- | --- | --- |
| `0.8.x` | `c2kb-file/1`、`0.8.3` | 维持双版与旧协议支持；新增只读升级预览及可选检索产物改进；已发布检索扩展不就地改写 |
| `0.7.x` | `c2kb-file/1`、`0.8.3` | 新项目默认独立编号；旧项目按原编号保持校验、发布与审计；显式迁移只改工作源配置 |
| `0.6.x` | `0.8.3` | 当前支持；可选本地运行账本与恢复，不改变知识文件协议、基础双版和默认发布行为 |
| `0.5.x` | `0.8.3` | 当前支持；默认双版与 registry 2.0 不变；关系映射、固定片段证据和候选扫描均为可选能力 |
| `0.4.x` | `0.8.3` | 当前支持；默认双版发布和 registry 2.0 不变；检索扩展、compact 为显式可选能力 |
| `0.3.x` | `0.8.3` | 兼容支持；新增一致性夹具和完整元数据说明，不要求改写已符合 0.8.3 的知识项目 |
| `0.2.x` | `0.8.3` | 知识文件协议兼容；工程已停止常规维护，建议升级参考实现 |
| `0.1.0` | `0.7.0` | 只保留历史说明；当前公开历史不承诺提供该标签、Release 或自动迁移器 |

## 升级 0.2.x 到 0.3.x

1. 更新 Code2KB Spec 工程或重新安装 `code2kb`；
2. 运行单元测试和 `scripts/check_conformance.py --check-expected`；
3. 对既有知识项目运行 `code2kb check`；
4. 只有项目校验报告出现真实协议差异时才修改知识文件。

本次工程升级没有改变知识规范版本、必填元数据、审核状态机或发布目录契约。0.2.x 生成的有效 0.8.3 项目无需为了版本号重新发布。

## 升级 0.3.x 到 0.4.x

更新工程后先对旧项目运行 `check` 和 `audit-release`。不创建 `Code2KB工程配置.json`、不使用检索命令时，保持原 full profile 与双版发布行为。要启用检索版，先在已审计的当前基础发布上执行 `retrieval-build`、`retrieval-evaluate`、`retrieval-audit`；下次发布可选 `--with-retrieval`。`compact` 仅适合重新编写并审核的知识源，不会自动改写旧正文。

## 升级 0.4.x 到 0.5.x

更新工程后可直接对旧项目运行 `check` 和 `audit-release`；没有 `关系映射.json` 的模块继续使用原审核与发布流程。启用关系扩展时，按[关系契约](relation-contract.md)为模块建立映射、复核证据和影响，再准备并批准新的发布包。关系清单随新发布生成；旧发布仍按对应 Git 提交或标签恢复后审计。`candidate` 与 `unresolved` 不会自动升级为已证实关系。此次升级不改变知识文件协议 `0.8.3`、基础版本清单或既有检索单元结构。

## 升级 0.5.x 到 0.6.x

更新工程后先对旧项目运行 `check` 和 `audit-release`。不使用 `run-create` 时，无需新建账本或改写已发布文件。要启用长任务接续，在知识项目的 `.gitignore` 加入 `.code2kb/`，确认 Git 已有提交，再使用[本地接续执行器](0.6.0-runner.md)。独立修改命令新增本地项目锁；硬退出后若提示未完成事务，先运行 `recover`。0.6 不自动重新批准、不自动推送或改变旧版知识格式。

## 升级 0.6.x 到 0.7.x：独立协议编号

旧 `0.8.3` 项目可以直接 `check`、准备、发布和 `audit-release`，无需迁移。新项目模板使用 `c2kb-file/1`。确需重编旧项目工作源编号时，先完成或取消运行、恢复未完成事务、将已审核包重新准备为 draft，并提交工作区；然后预演：

```bash
code2kb migrate-protocol --project-root /path/to/project --to c2kb-file/1 --dry-run
code2kb migrate-protocol --project-root /path/to/project --to c2kb-file/1 --apply --plan-sha256 <预演返回的摘要>
```

预演会列出配置前后摘要、旧发布摘要和需刷新的草稿包；已审核包会阻止迁移。执行会重新核对预演前提，只原子替换工作配置中的编号；不改已有 `发布/`、不批准候选或发布新版本。随后按现有审核流程准备并批准受影响包，使用新的 `release_id` 发布。旧历史版本从其 Git 提交的独立检出目录审计。[完整边界](protocol-id-migration-plan.md)。

## 升级 0.7.x 到 0.8.x

旧知识项目可照常 `check` 和 `audit-release`，无须重发基础双版。新检索单元聚合方式只在建立**新**检索扩展或新发布时生效；已有发布目录与清单保持原样。外部索引消费者应按[检索扩展契约](retrieval-contract.md)先建立新快照并核对全量，再切换受众指针。`preview-upgrade --module-id` 维持旧输出；需要全项目源码差异时显式使用 `--all-modules`，其结果为只读复核计划，不会替维护者修订事实或批准发布。

## 兼容声明边界

第三方实现按角色和规范编号声明兼容，不使用“整体兼容”替代覆盖清单。声明格式与运行方法见[一致性说明](conformance.md)。
