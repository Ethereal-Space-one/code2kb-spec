# Code2KB Spec 0.6.0 实施计划

> 状态：本地候选已实施，PR CI 与发布授权尚未完成。基线为已发布的 `v0.5.0`。本文只规划开源工程，不引入任何使用方的源码、知识项目、问答或运行数据。工程版本与知识文件协议版本独立；本版默认继续兼容现有 `0.8.3` 知识项目。

## 1. 目标与完成判定

0.6 的目标是让长时间知识提取任务在进程、会话或 Host 中断后，能根据**知识项目文件、Git 和持久运行账本**安全接续；同时让执行者知道当前任务允许写哪些文件、哪些步骤仍需人或既有策略授权。运行账本记录执行过程，不能取代规格、发布清单、Git 提交或发布快照成为新的事实来源。

本版完成时，应能在一个公开固定样本上从范围盘点走到单模块取证、影响复核、候选准备、审核、双版发布与审计；再在多模块样本上完成顺序处理和批次检查点。至少一次在真实进程终止后由新进程接续，证明不会重复批准、覆盖旧发布、跳过失败步骤或把未解决关系写成已证实事实。检索评测检查证据定位与受众隔离，不声称验证模型最终答复。

## 2. 当前基础与本版缺口

| 已有基础 | 0.6 要补的部分 |
| --- | --- |
| `check`、`impact`、`confirm-claims`、`prepare`、`approve`/`policy-review`、`publish`、`audit-release` 等命令已经存在 | 命令间缺少持久、可恢复的任务状态和统一的执行结果封装；现有命令仍须能独立调用 |
| 0.4 检索扩展可显式构建、评测与审计；0.5 关系和固定提交证据扩展可独立审计 | 把已启用的扩展纳入同一次候选与发布检查；未启用的项目不新增门槛 |
| 长任务指导要求从配置、功能大纲、发布清单和 Git 重建状态 | 提供机器可读的恢复检查、批次检查点和冲突报告；不凭聊天记录恢复批准状态 |
| 自动审核记录已有局部 `run_id` | 定义执行层 `run_id` 账本；两者身份与用途分开，不把执行 ID 当成审核凭据 |
| 0.5 已有事实关系、证据重建和覆盖报告 | 接续时复核固定提交、事实/关系摘要及影响队列，不能仅因任务曾标记完成就跳过 |

## 3. 设计边界

1. **保持默认行为。** 现有命令、成功输出、退出状态和基础双版发布流程维持兼容。统一 JSON 响应先作为显式选择，待实测覆盖后才考虑默认切换；扩展输出不能暗改知识文件协议、基础 registry 或当前版本指针。旧命令虽可独立调用，但所有受支持的修改入口必须与新执行器共用项目锁和副作用审计。
2. **先做执行内核，再做 Host。** CLI 是可测试的参考执行器；Host Adapter 只翻译任务输入、结果和工具调用，不能持有另一套状态机。Codex 已通过同契约对账，因此本版同时纳入 Claude Code 与 Codex 的薄适配；两者均不提供第二套状态或批准机制。
3. **账本不授权。** `completed` 仅表示该次任务输出通过可重建检查。`approve`、`policy-review`、`publish`、激活检索指针、远端推送和外部接入仍服从各自授权。现有 `retrieval-evaluate` 包含写报告、改清单与切换或删除指针的副作用，不能被执行器当作只读检查。执行者不得从旧对话、账本备注或 `check` 通过推断批准。
4. **不造“全自动提取准确率”。** 确定性工具可以盘点候选、检查证据和对账覆盖；事实归类、自然语言语义复核及业务意图确认仍需明确任务与证据。待核查、候选和未知保持原状态。
5. **文件边界要可审计。** 工具写入使用任务允许的 project-relative write set；源码仓库只读。事后差异审计只能证明已观测路径的变化，不能代替 Host 的文件系统权限隔离。禁止把运行账本、临时文件、凭据或内部工作稿放进发布检索目录。

## 4. 运行契约

### 4.1 任务与响应

定义带版本号的任务契约，最小字段为 `run_id`、`task_id`、`task_type`、`module_id`（可选）、项目路径、固定输入摘要、依赖任务、允许写入集合及所需授权类型。`task_id` 在一次运行中唯一；同一任务重试保留逻辑 ID、增加 attempt。执行任务明确区分确定性盘点、writer 正文写作、reviewer 语义复核、business-intent 证据确认、候选准备、批准/策略审核、Git 提交检查点、发布、检索构建/评测/激活与审计；各类 Agent 任务列明输入、受众、产物和谁负责验收。只实现本版贯通所需类型，不为未来功能预留空任务。`render-facts` 只给候选片段，不能代替 writer 或 reviewer。

CLI 增加显式机器输出模式（例如 `--output json`），返回固定 envelope：协议版本、命令、结果状态、稳定错误码、结构化结果、下一步建议和可定位的诊断项。成功与失败都必须是有效 JSON；stdout 只放机器响应，人读诊断走 stderr。先为执行器涉及的命令建立响应适配层，不一次性重写所有命令内部实现。保留旧 CLI 调用形式；对外明确各错误码与退出状态，区分输入错误、证据失效、内容冲突、待授权、可重试中断和内部错误。

### 4.2 持久账本与恢复

运行状态放在知识项目的独立内部目录（建议 `.code2kb/runs/<run_id>/`），不属于规范正文或发布物。账本采用带模式版本的确定性记录，至少保存任务输入摘要、attempt、开始/结束时间、状态、前置 Git HEAD、固定源码提交、允许与实际写入文件摘要、校验结果和检查点。禁止记录令牌、完整环境变量、未脱敏源码片段或私有问答。路径和日志保留策略写入使用文档。

状态至少区分 `pending`、`running`、`waiting_review`、`blocked`、`failed`、`completed` 和 `cancelled`；其中 `waiting_review` 是待外部决定，不是失败或完成。单个账本文件用临时文件和原子替换写入；这**不足以**保证多文件治理操作或发布安装的事务性，二者另有事务记录。同一知识项目同一时刻只允许一个修改型操作：独立的 `confirm-claims`、`prepare`、`approve`、`policy-review`、`publish`、检索构建/评测、恢复命令与 runner 共用项目锁；runner 内部调用避免重复获取锁。锁与账本分开：进程消失后先验证锁持有者和项目快照，不能只凭超时抢占。外部编辑无法靠项目锁阻止，须在写入前重核输入并于冲突时阻断。

恢复命令输出“可继续、需重跑、需复核、需授权、冲突阻断”的原因，并重新校验配置、固定提交、Git 状态、规格/关系摘要、发布清单及指针。判断已完成任务时，区分外部冲突与**经证明的后继任务合法覆盖**：例如 `approve` 正常改写 `prepare` 产生的 draft 正文和清单，不得因前一步整文件哈希变化就重跑 `prepare --refresh`。按任务保存语义输入、候选摘要、`content_digest`/`review_subject_digest` 等既有凭据与后继状态证明；只有这些证据能串成当前链路时才跳过，否则暂停复核。Git HEAD 允许经过显式提交检查点合法推进，不能一变就全部失效，也不能忽略被夹带的内容变化。

`prepare`、`approve`、`policy-review` 当前会逐文件改写正文和清单。0.6 为这些操作记录同一授权事务的前后像、候选摘要、预期文件集合和逐文件进度；恢复区分未开始、全部完成和部分完成。部分完成只能在原授权及摘要仍有效时继续同一事务，或回滚至前像；无法证明时阻断，不新造一次批准，也不把混合状态视为完成。提交发布输入和覆盖前提交旧发布目录是显式检查点：可由人或受约束的 Git 任务完成，账本核对提交所含路径与摘要，不从“存在新 HEAD”推断审核有效。

现有 `publish` 的回滚只覆盖可捕获异常，不能覆盖进程硬退出；0.6 必须补持久发布事务。事务记录旧/新发布身份、staging 与 backup 路径、安装阶段、指针和审计结果，恢复先识别未完成事务，再决定继续审计、恢复旧版或阻断；在恢复或回滚完成前不得删除备份、开始另一发布或把未审计新快照标为当前。至少在“旧目录移走后”“新目录安装后”“审计完成但账本未落盘”三个窗口注入真实子进程终止。不能重放 `approve` 或盲目重复 `publish`。旧发布审计只读冻结产物，不因工作稿后来变化而失败。

现有独立 `retrieval-evaluate` 会改发布目录中的报告、检索清单及当前检索指针；关系清单又绑定检索清单摘要。A 阶段先盘点全部现有命令的真实读写副作用。新 runner 只在有相应授权的发布事务 staging 中构建、评测、审计，并将检索清单、关系绑定和指针作为共同提交/恢复的产物；评测失败不触动既有就绪指针。既有独立 CLI 的兼容行为需单独写明并共享项目锁，不能用“新 runner 安全”冒充旧命令也已改变语义。

### 4.3 Write set 与任务边界

每种修改型任务给出精确路径或受限通配的允许写入集合，并在执行前展示；执行后比较 Git 与文件摘要，报告新增、修改、删除和越界文件。默认拒绝符号链接穿越、绝对路径写入、源码仓库写入，以及未经相应发布/检索事务授权而写发布目录。越界变化使任务失败并保留可审计差异，不自动删除用户文件。只读任务的实际 write set 必须为空；构建和评测检索扩展均为修改型任务。Host 能提供目录权限时应同时限制可写范围；本地 CLI 的 write-set 检查不宣称能阻止进程修改所有外部路径。内部账本加入公开知识项目的忽略模板，并以打包测试证明它不进入双版、检索单元或发布清单。

### 4.4 跨模块依赖与 Git 检查点

现有 `impact` 主要检查本模块，不能据此承诺跨模块精准失效。D 阶段增加只由已登记引用建立的依赖指纹：供方 `module_id#fact_id` 的结论与证据摘要 → 消费模块的关系/主题/正文任务。供方变化或删除时使实际消费者待复核；引用不完整或没有启用关系扩展时采用明确的保守降级并报告影响范围，不虚称精准。A→B、A 与 C 无关的公开夹具须证明 B 失效而 C 不被无故重跑；未知依赖不得被当成无影响。

发布输入提交与旧发布归档提交分别是账本检查点。允许 HEAD 只通过经核验的提交推进：核对提交包含的文件路径、内容摘要与授权快照，夹带无关变更时停止并提示复核。runner 不隐式 `git add .`、不自动推送远端；恢复从项目 Git 和文件现状重建，不从账本中的“提交完成”字样推断发布条件已满足。

## 5. 实施阶段与验收

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| A. 契约冻结 | 命令副作用清单、任务/状态/错误码/JSON 响应、账本格式、Agent 任务输入输出、Git 检查点和 write-set 规则；兼容矩阵 | 旧命令回归通过；同输入生成一致任务身份；失败响应可机读；明确 `retrieval-evaluate` 的变更与授权；不改变 0.8.3 发布文件 |
| B. 单模块垂直链 | 单模块任务序列、账本、状态查询、恢复与取消；`prepare`/批准/策略审核的多文件事务与提交检查点 | 新进程能从取证、复核、准备、批准后待提交的检查点接续；合法后继修改不使上游任务误失效；部分批准不能伪装完成 |
| C. 写入与发布恢复 | 全部修改入口共享项目锁和 write-set；持久发布事务、硬退出恢复与只读审计 | runner 与独立命令竞争被互斥；越界写入、旧审核摘要和三个发布硬退出窗口均能阻断或恢复；旧发布保持可审计 |
| D. 全库编排 | 从功能大纲生成模块任务顺序、已登记跨模块引用的依赖指纹和批次检查点；未归类与待核查报告 | 多模块样本能逐批推进；一个模块受阻不伪装全库完成；供方变化只使已知消费方失效，引用不全时保守降级 |
| E. Host 与检索闭环 | Claude Code 与 Codex 共用薄 Host Adapter；在有授权的 staging 事务中集成检索评测与 0.5 关系审计 | Host 不私存批准；CLI 与两个 Host 的任务状态等价；业务检索无研发泄漏；评测失败不改变旧清单绑定或就绪指针 |
| F. 发布候选 | 使用文档、故障恢复手顺、兼容报告、公开样本结果和 Release 材料 | 下文门禁全部通过，Python 3.9–3.13 PR CI 通过后合入受保护 `main` |

先做 A–C 的**一个模块、一条完整审核链和几个关键崩溃窗口**，确认状态、Git 检查点与文件边界成立，再扩至 D–E。不要为了模拟大型项目堆积没有独立失效机制的样例。Host Adapter 只在 CLI 契约稳定后接入。

## 6. 有意义的回归与发布门槛

公开夹具按故障模式选择，至少包含：`prepare`/`approve`/`policy-review` 每项的多文件半写后硬退出、批准后重启仍保持批准、批准后提交再重启、第二次发布时旧发布归档、夹带无关 Git 修改、runner 与独立命令争锁、三个发布事务窗口的子进程硬退出、同任务重试、输入摘要变化、未授权发布、越界写入、关系证据失效、检索评测失败后旧指针保持、业务/研发受众隔离、旧项目完全不启用运行账本。跨模块夹具使用供方 A、消费方 B、无关模块 C，分别验证引用变化、删除和未知依赖。每个失败夹具须证明会触发预期错误；正向夹具须证明不会误清合法批准，而非只确认代码运行。至少用一个与合成夹具独立且许可允许再分发的公开样本，走完真实跨进程单模块链路；它验证恢复和追溯，不被描述为生产问答质量证明。

开发期只运行受影响的任务契约、状态转移或发布恢复测试。改变文件协议、审核/发布语义、受众隔离或公共 CLI 时立即跑全量兼容回归。候选冻结时一次完成单元与集成测试、规范和一致性检查、公开内容/敏感扫描、Markdown 链接、独立公开样本、干净安装和 Python 3.9–3.13 CI；同一提交发版时核对标签与已通过 CI 的提交一致，不重复等价全套回归。

0.6 发布门槛为：跨进程恢复不跳步、不误清合法批准；失败、阻塞、取消及半写均不记为完成；任何越界文件变化可见且阻断后续自动步骤；独立修改命令与 runner 互斥；批准与策略审核的原有身份边界保留；三个硬退出窗口均能恢复旧版或确认完整新版，不能留下悬空当前指针；全库入口覆盖仍展示未归类/待核查；启用的检索与关系扩展共同审计通过，未启用项目的 0.5 默认流程不变。对无法强制隔离的写入范围、无法观察的外部副作用和未经运行验证的业务行为，报告中必须写清边界。

## 7. 不纳入 0.6

- 0.7 的统一多语言 Adapter SDK、语言能力分级和新增语言包；
- 1.0 的通用源码增量更新、重命名识别及增量/全量等价证明；
- 自动推断业务政策、运行环境真值、模型答复质量或自动批准；
- 生产机器人接入、Web 审核台、分布式任务队列、跨机器共享锁和云端托管服务。

## 8. 开工顺序

1. 从 `v0.5.0` 对应的 `main` 建立 0.6 分支，冻结兼容约束和公开故障夹具；先修正文档中已发现的工程版本旧字样，避免实施依据混乱。
2. 完成 A–C，提交一条可中断、可恢复、可审计的单模块端到端链路；审查状态记录是否与真实文件、Git 和授权一致。
3. 在这条链路稳定后完成 D–E；每阶段仅做能发现具体回归的验证，并记录尚不可证明的边界。
4. 候选冻结后做一次完整回归和独立复核；经 Pull Request、CI 和用户发布授权再创建 `v0.6.0` 标签与 Release。

本文是实施计划，不构成批准知识包、发布项目内容或创建公开 Release 的授权。
