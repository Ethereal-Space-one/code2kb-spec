# Code2KB Spec 1.0.0 技术实施规划

> 状态：1.0.0 发布候选，尚未合并或创建 GitHub Release。2026-10-27 根据公开案例与用户决定收口为**只读升级计划**。阶段 0、A、B 已完成；阶段 C 做了双模块手工基线迁移演练，五模块案例仅量测只读计划范围。公开消费契约已起草；自动迁移与任务账本衔接推迟，不作为 1.0 发布承诺。Python 3.9–3.13 的 PR CI 全部通过；GPT-6.1 Terra 独立审查指出的问题已修复并复核关闭。基线为已发布的 `v0.8.0`。只使用公开源码、公开样本和独立知识项目；不纳入使用方专有知识、源码或机器人配置。

## 1. 目标与边界

1. 在 0.8.0 全项目源码升级预览上提供**有证据边界的只读复核计划**，报告可疑模块、全局基线迁移成本、输入摘要与回退原因。`selected_modules` 只指语义复核候选，不自动迁移知识源、创建任务、批准或发布。
2. 用同一目标源码提交的独立标注案例对照计划范围；新增或未归属路径、旧运行证据和未证实关系应回退全项目。没有完成自动迁移和全量产物对账时，不宣称自动增量执行安全或节省人工工时。
3. 冻结一组小而明确的只读 CLI/JSON、既有检索产物和 Adapter 公共契约，给第三方消费端提供兼容测试。1.0 不要求接入真实机器人或生产索引。
4. 先补一个已复现的受众隔离缺口：业务文件当前可能携带源码仓库 URL 而通过校验。只拦源码导航链接，不引入新的索引结构或写作启发式体系。

成功不是“候选模块少”，而是：变化路径均得到解释；公开案例中应复核的模块无漏选；失败、过期或覆盖不全会阻断或回退；历史发布仍可审计；公开兼容示例在受支持环境可重现。刚讨论的任务关键词路由、索引分片和依赖展开方案不进入本版。

## 2. 现有基础与实际缺口

- `preview-upgrade --all-modules` 已比较旧、新固定 Git 提交，给出变化路径、证据变化、事实/主题、可能模块和降级建议；它明确只读，`possible_modules` 不是可直接放行的完整性证明。
- `run-create` 已支持按模块列名建立任务，但 writer 的现有 write set 不覆盖跨模块基线迁移。1.0 不把只读计划接入该账本；相关权限与恢复设计留给后续版本。
- 现有 `impact → confirm-claims → prepare → approve/policy-review → publish → audit-release` 已管理事实变更到发布；检索快照另有完整导入、切换和审计契约。
- 缺口是：只读计划虽已绑定输入并保守回退，却不能安全地执行跨模块基线迁移；自动增量的全量产物对账和净工时收益均无证据，故不进入 1.0。公共兼容边界仍需最终冻结。
- 阶段 0 前，业务扫描虽能拒绝大量代码标识和过程用语，仍会放过 `https://github.com/example/repo` 等使用中性标签的仓库链接。现已增加窄规则与冻结旧发布回归；这一历史漏检不表示已有发布物发生泄漏。

## 3. 技术方案

### 3.0 业务版源码链接隔离补洞

在现有业务内容校验路径中增加一条窄规则：识别常见代码托管仓库 URL，以及具有明确源码浏览路径形态的链接；覆盖业务知识源、业务版生成正文与导航/发布信息、可选业务检索单元。研发版保持现有证据表达，不增加网页链接配置或渲染器。链接检查只补现有术语扫描的漏项，不重写术语规则，也不把普通业务网页链接一概拒绝。

验收先固定正反例：上述两个漏过样例必须被拒绝；带正常业务网页链接的正文必须通过；源码路径、提交页、不同大小写、Markdown 链接与裸 URL 均有针对性测试。`check` 与新发布构建使用相同判定规则。`audit-release` 当前会在核对摘要后重新执行**当前**业务扫描，故不能只说“旧清单不改”就视为兼容；需将旧发布所用规则与新发布 URL 规则明确分开，保留旧版结构、摘要及旧业务规则检查。对无法识别的私有托管域名明示规则边界，不宣称已阻断所有企业内网链接。

兼容夹具须由 0.8 版生成并冻结，包含上述旧规则允许的源码 URL。新工具下验收：旧发布仍可审计；同内容的新构建被拒；清理知识源后能发布并审计新版本。另覆盖 `c2kb-file/1`、兼容 `0.8.3` 与显式启用检索扩展的路径。旧发布不修改，审计也不能因为选用旧规则而跳过原有结构与逐文件摘要检查。

历史发布的可审计性与当前知识源的可发布性分开：旧发布保持可审计；仍含源码仓库链接的旧知识源升级后会在 `check` 中提示修订，须重新走既有影响复核与审核流程才能发布新版本。这不是对历史审核状态的追认或撤销。

新发布的规则选择不得交给使用方开关；参考实现可用清单中已有、由发布器写入的生成工具版本区分历史与 1.0 及以后发布。此版本声明是兼容性标记，不是对恶意伪造本地发布物的身份认证；发布工具必须始终按当前规则校验新输入。最终发布前须核对工程 `VERSION` 与实际新发布采用的规则一致。

### 3.1 组件变化与反向影响

先复用 Git blob、证据快照、关系图和 Adapter 候选。对新增、删除、内容变化、类型变化逐项报告；只有现有 Adapter 明确声明且能验证的结构才细分，目前主要按文件与证据摘录保守定位。移动/重命名只能提供候选定位，不能沿用旧 `verified` 证据。无法识别结构的语言维持 L1 文件级降级。

反向影响记录从源码组件、证据到事实、正文、检索主题/单元及发布版本的可核对路径。只有已验证的边可用于确定性传播；`candidate`、`unresolved` 和隐含调用须进入待取证或回退原因。生成一个只读计划，至少包含旧/新完整源码提交、知识项目 Git 基线、配置/关系/发布清单摘要、逐路径覆盖状态、受影响事实与消费者、建议复核模块、未知项、回退等级及理由。保持 0.8 默认预览响应不变；增量计划使用显式新输出和独立 schema。

### 3.2 安全选择与任务衔接

计划判定只有 `selected_modules` 与 `full_project_review`，两者都不授权执行。`none_observed` 仅是观察结果，不可作为自动跳过的许可。只有变化路径及已记录的事实消费者和入口有充分归属，且没有阻断传播的未解边时，才可报告部分模块为**语义复核候选**；未选模块的旧证据能否重建仍是独立门槛。新增或未归属路径、已记录的外部实现未知、Adapter 能力不足、证据摘要失效、过期输入或关系图缺口，至少回退到相关模块；无法界定模块时回退全项目。人工排除路径须留理由和审核记录，不能被工具认定为已证明无影响。

**1.0 不把计划传给 `run-create`。**如后续版本考虑建立选定模块的语义复核任务，必须先实现受控基线迁移，再在任务创建前重新验证输入提交与摘要；版本变化拒绝沿用旧计划。候选知识项目、writer 权限、审核门槛和恢复机制需要独立设计，不把当前只读计划伪装成执行许可。

**基线迁移是独立硬门槛。** 当前项目配置为每个仓库保存一个全局固定提交；声明使用该仓库的模块，其 `source_revisions` 中对应提交必须与配置一致，相关证据快照也绑定该提交。仅选择部分模块并保留其他依赖该仓库的模块原文件，在切换全局提交后无法通过现有 `check`，更不能直接发布。因此必须先设计受控的跨模块基线/证据迁移：逐模块核对旧、新 Git 对象，重建可证明未变的证据，列明改动的配置、规格、关系、清单及其 write set，并重新判断受影响发布包的审核状态。原批准不得静默继承；若需批量确认，仍须走现有明确授权或策略审核门槛。此处“增量”仅指减少重新解释业务语义的模块数，**不承诺只修改被选模块的文件**。若无法安全完成迁移、审核或得到实测收益，则本轮回退全量复核，不上线选择性执行。

公开双模块技术演练已证明手工路径可闭环：目标提交只改变订单规则，预览选择订单；账户源码对象与摘录摘要不变，但证据快照中的提交号仍需更新。两模块重新准备并获得测试用明确批准后，新版可发布且旧版仍可审计。此演练只证明机制可行，不能替代受控迁移实现或独立业务答案复核；真实项目收益仍须按复核工时与改动范围实测。

**下一道投入闸门的实测结果：**双模块案例中，语义复核范围为 1/2，但基线迁移与发布包重审范围均为 2/2。现有任务账本在首个 writer 前运行全库 `check`，并从创建时锁定配置摘要；writer 的写入范围也不含全局配置。因此不能把这份旧基线计划直接传给 `run-create`：先迁移会使旧计划过期，后迁移会使运行账本失效。当前只读命令可复算 `plan_sha256` 拒绝过期输入，但**不提供自动任务衔接或自动迁移**。如要实现阶段 D，须先用更大且独立标注的公开案例证明省下的实际复核工时足以抵偿新增的候选隔离、跨模块迁移事务和账本状态；否则保留只读计划，沿现有全量审核流程执行，不宣称增量执行能力。

五模块范围复核使用 PetClinic REST 同一固定提交中的 Owner、Pet、Visit、Vet、Specialty 控制器；逐模块答案差异先写入 `conformance/upgrade-petclinic-five-module/expected.json`，再运行只读计划。第二提交只把 Owner 的空白姓氏改为查询全部主人。对照结果如下，其他四个文件的 Git blob 逐一确认未变：

| 公开案例 | 语义复核 | 基线文件触及 | 发布包审核刷新 | 证据摘录 |
| --- | ---: | ---: | ---: | --- |
| 自编双模块 | 1/2 | 2/2 | 2/2 | 一条变化、一条可重建 |
| PetClinic 五模块 | 1/5 | 5/5 | 5/5 | 一条变化、四条可重建；共 15 个文档的提交声明需刷新 |

五模块数字来自**临时知识元数据夹具和实际只读计划**，未经过五模块的 `check → approve → publish`、独立全量产物对账，也没有测得人工工时。因此它只证明语义复核候选可缩小，同时证实基线迁移与批准工作没有缩小；不足以解除阶段 D 的投入闸门。用户已决定 1.0 保留只读计划；若后续版本要重启任务衔接，须在许可明确的公开知识项目中量测完整迁移和审核触点，并证明净收益。

运行/部署证据若绑定本次升级仓库的旧提交，计划须列出证据路径并回退全项目复核；旧运行观察不能靠更换提交号变成新版本证据。这类证据不计入上述 source-only 双模块样本的 2/2 发布包数字。

### 3.3 独立预期对照与发布边界

对同一目标源码提交先独立标注会改变答案的事实，再对照只读计划的选中与回退范围；标注须先于工具结果固定。五模块案例只比较源码、答案标注及复核范围，不等同于增量发布与全量发布的产物对账。若以后提供自动迁移，才须增加两条实际发布链路，对事实、回答关键断言、正文、检索单元、审核记录与文件摘要进行独立全量对账。

常规知识项目发布仍须生成新 release，运行既有 check、影响确认、检索回归、准备、批准、审计；旧版本不覆盖。1.0 的升级计划不会触发其中任何写入。案例记录能实测的复核模块数与文件数；未测得的人工触点和耗时不得写成收益。若出现漏选，应修复或回退全项目。

### 3.4 稳定公共契约

在只读计划与案例对照通过后，列出并冻结实际给外部使用的最小表面：CLI 参数与退出码、稳定 JSON 字段和版本协商、`c2kb-file/1` 及已启用扩展的检索产物、Adapter SDK 的能力声明和 L1/L2/L3 降级语义。对未承诺稳定的诊断字段明确标注实验性；保留 0.8 命令默认行为及旧文件协议兼容路径。

候选白名单已写入[1.0 公开消费契约](1.0.0-public-contract.md)。只读计划的核心字段可供展示与过期核对；明细诊断不成为自动授权接口。最终冻结以发布前的跨 Python 版本 CI 和独立审查为准。

MCP 如需提供，仅是同一参考服务层的薄包装；Claude Code、Codex 和第三方消费者只通过相同契约测试验证输入输出与错误行为，不另建状态机或授权逻辑。生产机器人、数据库和任意语言的 L3 语义支持不作为 1.0 发布前提。

## 4. 实施顺序与验收门槛

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 0. 受众隔离补洞 | 在现有校验路径增加源码链接识别与最小正反例 | 已复现的漏过样例失败；普通业务链接通过；源文件、基础业务版、可选业务检索单元同口径；含旧 URL 的 0.8 冻结发布仍可完整审计 |
| A. 公共案例与判定基线 | 许可明确的双提交公开源码、独立标注的事实/消费者/模块预期 | 预期答案先由独立阅读源码形成，不能从工具输出反填 |
| B. 只读计划 | 逐路径覆盖、反向影响、输入摘要、选择/回退理由 | 同一输入稳定；Git 与知识项目零修改；0.8 预览兼容 |
| C. 基线迁移闸门 | 明确全局配置、未选模块证据刷新、关系摘要和审核失效的处理与成本 | 两模块共用一个仓库，仅一模块语义变化；未变模块在新提交下可核验，新发布成功且授权记录完整；否则回退全量 |
| D. 任务衔接 | **推迟至后续版本**；1.0 保留只读计划 | 计划不修改项目，也不接受为 `run-create` 的输入 |
| E. 独立预期对照 | 同目标提交的独立答案标注与只读计划范围对照 | 公共案例不漏会改变答案的模块；未知覆盖退回全项目；不声称产物级增量等价 |
| F. 契约冻结 | CLI/JSON、检索、Adapter 兼容声明与消费者契约测试 | Python 3.9–3.13 CI、全新安装、旧项目读取/审计、两个 Host 的薄适配通过 |
| G. 发布审核 | 公开内容审计、独立代码/产物审查、PR CI | 无专有内容；安全边界与实测结果一致；发现真实问题先修复再发布 |

重点案例保持少而能揭示不同失效机制：已验证证据改变答案；跨模块事实消费者；新增或未归属路径；仅移动但未重建证据；候选/未解边；计划过期；删除或受众迁移后的检索快照。前两项证明只读范围选择，后几项证明降级、拒绝旧计划和既有发布对账；1.0 不测试尚未实现的自动迁移中断恢复，也不宣称增量执行能力成熟。

## 5. 不纳入本版

- 自动改写业务结论、升级证据等级、推断业务政策或线上运行结果；
- 自动基线迁移、计划接入任务账本、选择性执行与增量发布；
- 自动批准、激活发布版本或把候选关系当作已验证关系；
- 生产 FTS/向量服务、机器人问答链路、关键词路由与索引分片；
- Kit 式模块检索卡片、整套 `retrieval_quality` 写作启发式和源码网页链接渲染；三者目前缺少在 Code2KB 检索链路上具有实质收益的对照证据；
- 多人并发知识编辑、通用重命名证明、所有语言的 L3 Adapter；
- 对旧知识文件协议做破坏性更改，或把使用方知识库升级当作本工程的发布内容。

## 6. 已定边界与后续问题

1. 只读计划使用 `preview-upgrade --all-modules --plan` 显式输出；默认预览 JSON 保持兼容。`--expect-plan-sha256` 只做过期核对。
2. 公开双模块与五模块标注先于计划固定。归属不明、未证实关系、旧运行证据等条件回退全项目；空影响不代表可以跳过审核。
3. 1.0 只冻结[最小消费字段](1.0.0-public-contract.md)；诊断明细和具体原因字符串不作自动决策契约。
4. 跨模块基线迁移、未选模块证据重建、审核刷新和任务账本衔接推迟。已有双模块手工演练不能替代受控工具或人工工时收益证据。
5. 新发布使用当前 URL 隔离规则；历史发布按其生成工具版本使用原规则，同时仍核对结构和逐文件摘要。冻结旧发布夹具用于回归。
