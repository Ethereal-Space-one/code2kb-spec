# Code2KB Spec 1.0.0 技术实施规划草案

> 状态：审查后修订稿；阶段 0 已完成。阶段 A 的公开双模块源码与独立预期已固定；阶段 B 的只读候选计划已用双模块技术夹具验证，并增加输入过期核对与复核范围计数。阶段 C 已做手工基线迁移演练：仅订单语义变化，但两模块的固定提交、证据与审核记录均须更新；受控迁移工具尚未实现。阶段 D–G 未实施，1.0 尚未发布。基线为已发布的 `v0.8.0`。只使用公开源码、公开样本和独立知识项目；不纳入使用方专有知识、源码或机器人配置。

## 1. 目标与边界

1. 把 0.8.0 的只读全项目源码升级预览接到现有任务账本，完成**有证据边界的增量复核**。增量的含义是选择需要重新取证和审核的模块；业务结论仍由复核者修订，不由工具自动改写。
2. 用同一目标源码提交的独立全量复核作对照，证明选择性复核没有漏掉会改变答案的事实、正文或检索单元。不能证明时回退全量。
3. 在验证上述链路后，冻结一组小而明确的 CLI/JSON、检索产物和 Adapter 公共契约，给第三方消费端提供兼容测试。1.0 不要求接入真实机器人或生产索引。
4. 先补一个已复现的受众隔离缺口：业务文件当前可能携带源码仓库 URL 而通过校验。只拦源码导航链接，不引入新的索引结构或写作启发式体系。

成功不是“候选模块少”，而是：变化路径均得到解释；应复核的模块无漏选；失败、过期或覆盖不全会阻断或回退；新旧发布版本可审计；公开兼容示例在受支持环境可重现。刚讨论的任务关键词路由、索引分片和依赖展开方案不进入本版。

## 2. 现有基础与实际缺口

- `preview-upgrade --all-modules` 已比较旧、新固定 Git 提交，给出变化路径、证据变化、事实/主题、可能模块和降级建议；它明确只读，`possible_modules` 不是可直接放行的完整性证明。
- `run-create` 已支持按模块列名建立任务，writer 的现有 write set 是该模块 `知识源/` 目录、`知识源/功能大纲.md` 和该模块 `运行证据/` 目录；审核与发布使用同一账本。1.0 应复用这套权限及恢复机制。
- 现有 `impact → confirm-claims → prepare → approve/policy-review → publish → audit-release` 已管理事实变更到发布；检索快照另有完整导入、切换和审计契约。
- 缺口是：预览不能安全地决定何时只建部分模块任务；计划与输入版本尚未绑定；未选模块与全量结果没有系统对账；公共兼容边界尚未最终冻结。
- 当前业务扫描已能拒绝大量代码标识和过程用语，但使用中性标签的仓库链接仍可能漏过。以现有扫描函数核对，`https://github.com/example/repo` 和 `[参考](https://github.com/example/repo/blob/abc1234/README.md#L3)` 均被接受。这是可复现的校验缺口，不表示已有发布物发生泄漏。

## 3. 技术方案

### 3.0 业务版源码链接隔离补洞

在现有业务内容校验路径中增加一条窄规则：识别常见代码托管仓库 URL，以及具有明确源码浏览路径形态的链接；覆盖业务知识源、业务版生成正文与导航/发布信息、可选业务检索单元。研发版保持现有证据表达，不增加网页链接配置或渲染器。链接检查只补现有术语扫描的漏项，不重写术语规则，也不把普通业务网页链接一概拒绝。

验收先固定正反例：上述两个漏过样例必须被拒绝；带正常业务网页链接的正文必须通过；源码路径、提交页、不同大小写、Markdown 链接与裸 URL 均有针对性测试。`check` 与新发布构建使用相同判定规则。`audit-release` 当前会在核对摘要后重新执行**当前**业务扫描，故不能只说“旧清单不改”就视为兼容；需将旧发布所用规则与新发布 URL 规则明确分开，保留旧版结构、摘要及旧业务规则检查。对无法识别的私有托管域名明示规则边界，不宣称已阻断所有企业内网链接。

兼容夹具须由 0.8 版生成并冻结，包含上述旧规则允许的源码 URL。新工具下验收：旧发布仍可审计；同内容的新构建被拒；清理知识源后能发布并审计新版本。另覆盖 `c2kb-file/1`、兼容 `0.8.3` 与显式启用检索扩展的路径。旧发布不修改，审计也不能因为选用旧规则而跳过原有结构与逐文件摘要检查。

历史发布的可审计性与当前知识源的可发布性分开：旧发布保持可审计；仍含源码仓库链接的旧知识源升级后会在 `check` 中提示修订，须重新走既有影响复核与审核流程才能发布新版本。这不是对历史审核状态的追认或撤销。

新发布的规则选择不得交给使用方开关；参考实现可用清单中已有、由发布器写入的生成工具版本区分历史与 1.0 及以后发布。此版本声明是兼容性标记，不是对恶意伪造本地发布物的身份认证；发布工具必须始终按当前规则校验新输入。最终发布前须核对工程 `VERSION` 与实际新发布采用的规则一致。

### 3.1 组件变化与反向影响

先复用 Git blob、证据快照、关系图和 Adapter 候选。对新增、删除、内容变化、类型变化逐项报告；可识别的签名、方法体和依赖边变化通过 Adapter 能力声明细分。移动/重命名只能提供候选定位，不能沿用旧 `verified` 证据。无法识别结构的语言维持 L1 文件级降级。

反向影响记录从源码组件、证据到事实、正文、检索主题/单元及发布版本的可核对路径。只有已验证的边可用于确定性传播；`candidate`、`unresolved` 和隐含调用须进入待取证或回退原因。生成一个只读计划，至少包含旧/新完整源码提交、知识项目 Git 基线、配置/关系/发布清单摘要、逐路径覆盖状态、受影响事实与消费者、建议复核模块、未知项、回退等级及理由。保持 0.8 默认预览响应不变；增量计划使用显式新输出和独立 schema。

### 3.2 安全选择与任务衔接

可执行结论只有 `selected_modules` 与 `full_project_review`。`none_observed` 仅是观察结果，不可作为自动跳过的许可。只有变化路径、已发布事实消费者和相关入口均能得到充分归属，旧证据可重建，且没有阻断传播的未解边时，才可选部分模块。新增或未归属路径、外部实现未知、Adapter 能力不足、证据摘要失效、过期输入或关系图缺口，至少回退到相关模块；无法界定模块时回退全项目。人工排除路径须留理由和审核记录，不能被工具认定为已证明无影响。

计划被维护者接受后，才考虑用现有 `run-create` 建立选定模块的**语义复核**任务。创建前重新验证输入提交与摘要；版本变化则拒绝沿用旧计划。任务仍遵守现有 write set 与审批门槛，不增加“自动批准”通道。候选知识项目用独立 Git 检出，源码只读固定对象；中断、越界写入和账本恢复仍按现有机制处理。

**基线迁移是独立硬门槛。** 当前项目配置为每个仓库保存一个全局固定提交；声明使用该仓库的模块，其 `source_revisions` 中对应提交必须与配置一致，相关证据快照也绑定该提交。仅选择部分模块并保留其他依赖该仓库的模块原文件，在切换全局提交后无法通过现有 `check`，更不能直接发布。因此必须先设计受控的跨模块基线/证据迁移：逐模块核对旧、新 Git 对象，重建可证明未变的证据，列明改动的配置、规格、关系、清单及其 write set，并重新判断受影响发布包的审核状态。原批准不得静默继承；若需批量确认，仍须走现有明确授权或策略审核门槛。此处“增量”仅指减少重新解释业务语义的模块数，**不承诺只修改被选模块的文件**。若无法安全完成迁移、审核或得到实测收益，则本轮回退全量复核，不上线选择性执行。

公开双模块技术演练已证明手工路径可闭环：目标提交只改变订单规则，预览选择订单；账户源码对象与摘录摘要不变，但证据快照中的提交号仍需更新。两模块重新准备并获得测试用明确批准后，新版可发布且旧版仍可审计。此演练只证明机制可行，不能替代受控迁移实现或独立业务答案复核；真实项目收益仍须按复核工时与改动范围实测。

**下一道投入闸门的实测结果：**双模块案例中，语义复核范围为 1/2，但基线迁移与发布包重审范围均为 2/2。现有任务账本在首个 writer 前运行全库 `check`，并从创建时锁定配置摘要；writer 的写入范围也不含全局配置。因此不能把这份旧基线计划直接传给 `run-create`：先迁移会使旧计划过期，后迁移会使运行账本失效。当前只读命令可复算 `plan_sha256` 拒绝过期输入，但**不提供自动任务衔接或自动迁移**。如要实现阶段 D，须先用更大且独立标注的公开案例证明省下的实际复核工时足以抵偿新增的候选隔离、跨模块迁移事务和账本状态；否则保留只读计划，沿现有全量审核流程执行，不宣称增量执行能力。

运行/部署证据若绑定本次升级仓库的旧提交，计划须列出证据路径并回退全项目复核；旧运行观察不能靠更换提交号变成新版本证据。这类证据不计入上述 source-only 双模块样本的 2/2 发布包数字。

### 3.3 全量对账与发布

对同一目标源码提交准备一份独立全量复核结果，作为增量方案的判定基线。对账范围是事实集合、回答关键断言、正文与检索单元的身份/受众/来源、发布清单和文件摘要。对于模型撰写的自由文本，不要求字节相等；差异必须由独立复核者判定是否改变答案、遗漏限制或泄露受众。只有确定性派生产物才要求字节级或结构级等价。

发布必须生成新 release，运行既有 check、影响确认、检索回归、准备、批准、审计；旧版本不覆盖。记录增量和全量的实际复核模块数、文件数、人工触点、耗时及差异，不用单一演示样本外推普遍收益。对账不能完成或发现漏选时，不发布“增量安全”结论。

### 3.4 稳定公共契约

在增量闭环通过后，列出并冻结实际给外部使用的最小表面：CLI 参数与退出码、稳定 JSON 字段和版本协商、`c2kb-file/1` 及已启用扩展的检索产物、Adapter SDK 的能力声明和 L1/L2/L3 降级语义。对未承诺稳定的诊断字段明确标注实验性；保留 0.8 命令默认行为及旧文件协议兼容路径。

MCP 如需提供，仅是同一参考服务层的薄包装；Claude Code、Codex 和第三方消费者只通过相同契约测试验证输入输出与错误行为，不另建状态机或授权逻辑。生产机器人、数据库和任意语言的 L3 语义支持不作为 1.0 发布前提。

## 4. 实施顺序与验收门槛

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 0. 受众隔离补洞 | 在现有校验路径增加源码链接识别与最小正反例 | 已复现的漏过样例失败；普通业务链接通过；源文件、基础业务版、可选业务检索单元同口径；含旧 URL 的 0.8 冻结发布仍可完整审计 |
| A. 公共案例与判定基线 | 许可明确的双提交公开源码、独立标注的事实/消费者/模块预期 | 预期答案先由独立阅读源码形成，不能从工具输出反填 |
| B. 只读计划 | 逐路径覆盖、反向影响、输入摘要、选择/回退理由 | 同一输入稳定；Git 与知识项目零修改；0.8 预览兼容 |
| C. 基线迁移闸门 | 明确全局配置、未选模块证据刷新、关系摘要和审核失效的处理与成本 | 两模块共用一个仓库，仅一模块语义变化；未变模块在新提交下可核验，新发布成功且授权记录完整；否则回退全量 |
| D. 任务衔接 | 迁移闸门通过后，显式接受计划并调用现有账本，隔离候选项目 | 过期计划、未归属路径、越界写入、错误恢复均失败封闭；无自动批准 |
| E. 全量对账 | 同目标提交的增量与全量复核记录及差异报告 | 不漏会改变答案的事实/模块；未选模块证据迁移与审核可解释；受众和未知边界保持 |
| F. 契约冻结 | CLI/JSON、检索、Adapter 兼容声明与消费者契约测试 | Python 3.9–3.13 CI、全新安装、旧项目读取/审计、两个 Host 的薄适配通过 |
| G. 发布审核 | 公开内容审计、独立代码/产物审查、PR CI | 无专有内容；安全边界与实测结果一致；发现真实问题先修复再发布 |

重点案例保持少而能揭示不同失效机制：已验证证据改变答案；跨模块事实消费者；新增或未归属路径；仅移动但未重建证据；候选/未解边；计划过期与中断恢复；删除或受众迁移后的检索快照。前两项证明选取正确，后五项证明降级、阻断和发布对账正确。若公开案例无法证明选择性复核有实际范围收益，可以先交付只读计划与对账，但不宣称增量能力成熟。

## 5. 不纳入本版

- 自动改写业务结论、升级证据等级、推断业务政策或线上运行结果；
- 自动批准、激活发布版本或把候选关系当作已验证关系；
- 生产 FTS/向量服务、机器人问答链路、关键词路由与索引分片；
- Kit 式模块检索卡片、整套 `retrieval_quality` 写作启发式和源码网页链接渲染；三者目前缺少在 Code2KB 检索链路上具有实质收益的对照证据；
- 多人并发知识编辑、通用重命名证明、所有语言的 L3 Adapter；
- 对旧知识文件协议做破坏性更改，或把使用方知识库升级当作本工程的发布内容。

## 6. 实施前需要确定的设计点

1. 增量计划采用独立只读命令，还是现有预览的显式附加输出；必须保持默认 JSON 兼容。
2. 哪些覆盖条件足以把回退范围从全项目缩到模块；应由公开案例和负例决定，不能凭无边推定安全。
3. 独立全量复核如何固定人工结论，避免拿增量结果反向填充“基线”。
4. 1.0 首批稳定字段的白名单、兼容期限及实验字段标记；仅冻结已有消费者真正需要的部分。
5. 基线迁移的操作边界、逐模块证据重建和审核失效规则；若无法在公开两模块案例里闭环，应停止选择性执行，而不是放宽 `source_revisions` 或沿用旧批准。
6. 新发布与历史 `audit-release` 选用 URL 隔离规则的版本依据；不能凭当前工具版本重新判旧发布违规，也不能使新发布伪装成旧规则绕过隔离。
