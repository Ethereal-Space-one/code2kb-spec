# Code2KB Spec 0.7.0 实施计划

> 状态：实施中。公开基线为 `v0.6.0`。本计划只使用开源仓库与获许可的公开样本；不读取、复制或修改任何使用方知识项目。工程版本、文件协议兼容标识与知识项目 `release_id` 分别演进。

## 1. 产品目标与完成判定

Code2KB Spec 从**固定源码提交**提取有证据的业务行为和代码逻辑，形成可复核、可发布、适合检索问答的知识库。业务知识包含代码可观察的流程、条件、计算、状态和异常分支；研发知识包含入口、调用、方法、数据和依赖。代码不能单独证明业务政策的原因、线上运行结果或外部服务内部行为，这些未知须保留在事实和检索内容中。

0.7 的 Adapter 平台服务于这条链路的**发现与取证**，不是以扫描文件数或识别方法数为最终成果。候选必须经过固定提交证据复核、事实归类和既有审核，才能进入业务版、研发版和检索版。完成判定至少包含一个获许可的公开混合语言样本，从源码候选经复核事实走到双版正文和可定位出处的检索单元；无法证明的跨语言关系保持 `unresolved`。此链路验证证据与知识产物，不虚称验证模型最终答复或线上行为。

同时完成 [公开协议编号迁移 Issue #5](https://github.com/Ethereal-Space-one/code2kb-spec/issues/5)。新项目建议采用 `c2kb-file/1`；旧 `0.8.3` 项目继续检查、准备、发布和审计。新标识只有在确认文件结构和语义没有变化后才能作为兼容重编；若发现语义变更，须另列格式契约和夹具。

## 2. 当前实现与必须消除的耦合

| 当前实现 | 0.7 必须补足 |
| --- | --- |
| `validation/knowledge.py` 以单一 `STANDARD_VERSION` 同时表示模板默认值和可接受格式 | 分开默认写入、可读取版本、协议能力；未知编号失败封闭 |
| `validation/governance.py` 的发布审计要求清单版本等于当前常量 | 审计按清单自身声明的受支持格式执行；指针与清单仍须一致 |
| 业务意图、业务证据和 `intent_included` 通过当前版本号分支判断 | 按协议能力验证；旧项目不能因默认编号变化而放宽校验或被拒绝 |
| 0.6 Runner 把完整配置摘要存入运行账本 | 活跃运行和未完成事务阻止迁移；不重写旧账本摘要 |
| `analyze-candidates` 使用逐行正则，UniApp 盘点器另设接口 | 统一 Adapter 契约，保留旧 CLI payload 和 JSON envelope |
| 候选只有路径、行号和表达式 | 新格式须携带快照来源、临时组件身份、规则版本、能力上限和未解原因；已验证关系另需两端及证据 |

## 3. 协议迁移契约

1. 配置中的 `standard_version`、结构化规格中的 `spec_version`、发布清单及当前指针的协议字段分别列出读取和写入点。新建项目默认写新标识；旧项目不迁移仍使用旧标识。对未知标识分别在配置、发布清单和当前指针上测试拒绝行为。
2. `check → prepare → approve/policy-review → publish → audit-release` 对新旧有效项目各自通过；**同一项目**还要覆盖“旧发布 → 显式迁移工作源 → 新发布”。`publish` 在替换当前 `发布/` 前审计旧发布，不能因为旧清单编号而失败。
3. 迁移命令先执行完全无写的预演，输出拟修改文件、前后摘要、需刷新的草稿包及旧发布摘要；已审核包、活跃运行和未完成事务会阻止预演。预演不能创建 `.code2kb/` 或项目锁。执行必须消费预演摘要，在获取项目锁后重新核对输入、Git 状态和运行状态；过期计划拒绝执行。存在活跃运行或未完成事务时拒绝，不自动取消运行或重写其基线。
4. 迁移仅修改有定义的**工作源**配置和必要元数据；不改 `发布/`、旧 registry、当前指针、Git 标签，不自动批准或发布。迁移前后当前发布目录字节一致。之后正常发布仍按既有机制替换当前目录；旧历史版本需在原 Git 提交的独立检出目录审计，不承诺当前目录可直接审计任意旧版。
5. 若工作源或候选摘要改变，受影响模块重新准备和审核；下一次发布使用新 `release_id`。迁移失败不得留下半改配置。公开一致性夹具、规范、模板、CLI 输出与文档须同步声明新旧兼容范围。

## 4. Adapter 最小契约

Adapter 输入仅包含仓库逻辑 ID、固定 Git commit、受限扫描范围和经校验的 Adapter 配置；不得把工作区改动当作证据。第一版只执行内置、明确注册的 Adapter；第三方接口先公开契约与一致性测试，不默认加载任意项目代码。

新输出须说明 Adapter 名称与规则版本、仓库和提交、扫描范围、候选组件的类型、表达式、源码定位、发现规则、能力等级及 `candidate/unresolved` 状态。组件候选 ID 在**同一固定快照**重复扫描时稳定；路径移动和语义重命名后的长期身份仍由知识项目的显式 ID 与复核记录维护，不能把候选 ID 当作长期事实 ID。跨语言边只有在两端组件、各自证据和桥接依据明确时才能提出，解析不全应给出 `unresolved_reason`。Adapter 输出不直接产生 `verified` 事实。

能力按实际操作分级：L1 为文件与语言盘点；L2 为指定语法结构的确定提取；L3 为有解析依据的调用或数据关系。现有逐行正则只保留为保守候选，不能概括宣称 Java 或 TypeScript 已具备完整 L2/L3。UniApp/TypeScript 和 Java 先成为参考 Adapter；Shell、SQL、HTML/CSS、YAML、JSON、TOML 等辅助语言先统一提供 L1，后续逐语言以正反夹具证明 L2。未安装专用 Adapter 的语言仅做明确的 L1 降级，不冒充完整覆盖。

旧 `analyze-candidates` 默认 payload（schema `0.1`）和全局 `--output json` envelope（response schema `0.1`）保持兼容；新候选格式以显式选择启用。`inventory_adapter` 的 UniApp 配置保留旧行为，是否迁入统一扫描由可比较的输出夹具证明。若新增项目配置字段，须在严格字段校验中独立定义，不能混入“仅改协议编号”的兼容重编。

## 5. 实施阶段与门槛

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| A. 协议能力表 | 新旧编号、读写点和业务意图等能力矩阵；新旧夹具 | 旧项目校验强度不降低，未知格式失败封闭 |
| B. 连续迁移 | 无写预演、显式执行、Runner 阻断、旧发布审计与新发布 | 同一项目旧发布→迁移→新发布通过；活跃运行与过期预演均不写入 |
| C. Adapter 契约 | manifest、输入/输出 schema、候选身份与规则版本、L1/L2/L3 声明 | 同提交重复扫描稳定，误判样例保持 candidate/unresolved |
| D. 参考适配与知识闭环 | UniApp/TS/Java 接入、通用 L1、一个公开混合语言知识链路 | 旧 CLI 两种输出保持；有证据事实进入双版及检索，未知不被提升 |
| E. 候选冻结 | 规范、模板、兼容报告、公开内容扫描、回归记录 | Python 3.9–3.13 CI、独立公开样本和全量兼容回归通过 |

先完成 A–B 并单独审查，再做 C–D。协议编号与 Adapter 输出的变化分别核对、分别保留测试和文档；两条线共用的 CLI 接入可在同一候选提交中落地。每个阶段只跑相应测试；协议、发布审计、受众隔离或公共 CLI 变化时跑完整兼容回归；候选冻结时做一次全量回归，不反复运行等价测试。

## 6. 有意义的回归样例

- 使用 `v0.6.0` 生成并冻结的旧发布物，测试旧清单审计、指针错配与新发布前审计；不能全由改造后的生成器自产自验。
- 双协议下业务意图和业务证据的有效、缺项两组样例；迁移前后内容和旧发布摘要对账。
- 预演完整目录树零变化（含隐藏文件）；活跃运行、未完成事务、脏工作区、预演过期及执行中断分别失败封闭。
- Adapter 的注释/字符串伪声明、多行声明、同名组件、动态路由、Vue 多语言块、扫描范围排除、缺少专用 Adapter 的 L1 降级和跨语言桥接反例。新增夹具接入可执行测试与 CI，不能只列覆盖编号。
- 独立公开混合语言样本中至少一个“入口→接口→方法→可回答事实→检索主题”链条；业务版回答保留条件和未知，研发版保留实现出处，不能把外部服务未知写成已证明行为。

## 7. 明确不纳入

- 不自动推断业务政策原因、运行真值或服务端外部实现；不自动批准知识包。
- 不承诺所有语言达到 L2/L3，也不在本版实现通用重命名识别、增量与全量等价或生产机器人接入。
- 不修改任何使用方知识库、本地私有工具、既有公开标签或历史发布物。

本计划不构成对任何知识项目发布包的授权，也不授权创建 `v0.7.0` 标签、GitHub Release 或远端推送。
