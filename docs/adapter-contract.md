# 0.7 候选 Adapter 契约

Code2KB 的目标是从固定源码中提取**可回答的业务行为与代码逻辑知识**。Adapter 只负责发现可复核的源码候选。候选经过证据核对、模块归类、事实复核和发布审核后，才可进入业务版、研发版与检索单元。路径相同、方法同名或模型认为相似都不能直接证明调用关系或业务意图。

## 能力等级

| 等级 | 可以声明 | 不得暗示 |
| --- | --- | --- |
| L1 | 固定提交中的文本文件和语言线索 | 已解析程序结构 |
| L2 | 指定格式或语法的确定结构，例如标准 JSON 中已注册的 UniApp 页面 | 所有路由可达、部署一致 |
| L3 | 有两端和解析依据的调用或数据关系候选 | 自动成为已审核业务事实或运行真值 |

没有专用分析器的语言降级为 L1。当前逐行 TypeScript/Java 匹配仅为词法候选，即使表达式是字面量，也可能来自注释或不执行的代码；跨语言相同路由只输出 `candidate` 桥接边。后续每项 L2/L3 能力必须有正反夹具和能力边界。

## 输入和输出

参考入口为 `code2kb analyze-candidates --repository-id ID --candidate-schema 0.2 --project-root PROJECT`。可用 `--adapter builtin-mixed|universal-l1` 选择内置能力；后者只做 L1 文件盘点。可选 `--scope` 指定仓库内安全相对路径，`--uniapp-manifest` 指定已配置仓库内的标准 JSON 页面清单。默认不指定 `--candidate-schema` 时，仍输出旧 schema `0.1`；全局 `--output json` 的响应 envelope 也维持 `0.1`。

Adapter 输入是仓库逻辑 ID、完整固定 Git 提交、扫描范围和明确配置。输出 schema `0.2` 含：

- `adapter`：名称、规则版本和能力声明；
- `snapshot`：仓库 ID、实际解析后的提交、扫描范围；
- `coverage`：可读取的 UTF-8 文本文件数及跳过原因计数；
- `candidates`：候选 ID、语言、类型、表达式、源码锚点、发现规则、等级、状态与未解原因；
- `edges`：候选关系两端、各端锚点、发现依据及 `candidate/unresolved` 状态。

候选 ID 由仓库 ID、路径、类型、表达式及同类出现序号确定，同一固定快照重复扫描稳定。它是**发现阶段身份**，不承诺源码移动或语义重命名后仍稳定。知识项目的入口、接口、方法、事实和主题使用显式稳定 ID；迁移身份由复核者记录，不能让扫描器按文本相似度自动继承。

内置 Adapter 通过 `validation.adapters.sdk.CandidateAdapter` 接口和 `validate_result` 校验。候选输出禁止 `verified`；第三方 Adapter 需要先公开 manifest、夹具与能力边界，当前 CLI 不自动加载任意项目代码作为插件。

## 知识闭环

一条可用链路至少包括：固定源码入口 → 候选接口/方法 → 经证据复核的结构化事实 → 保留条件、失败分支及未知的业务正文和研发正文 → 已审核的检索单元与出处。外部服务、动态配置和运行结果若无独立证据，必须保留未知。Adapter 报告的文件数、候选数或边数不构成知识库完成率。
