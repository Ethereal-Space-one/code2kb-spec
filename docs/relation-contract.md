# 0.5 关系与证据扩展（实验契约）

此扩展为已审核知识的**追溯索引**。它不改变知识文件协议 `0.8.3`、双版版本清单或 0.4 检索单元结构；未启用的旧项目按原流程运行。`candidate` 和 `unresolved` 不表示业务行为已证实。业务检索仍只读取业务版与业务检索单元，不读取关系清单中的源码细节。

## 输入与身份

启用时，在模块的 `结构化规格.md` 同目录新建 `关系映射.json`。该文件是可编辑、需复核的关系输入；规格中的事实仍是结论源。示例和故意失败的文件见 `conformance/relations/`。JSON 必须使用下列字段，不能增删：

```json
{
  "schema_version": "0.1",
  "module_id": "example.query",
  "topics": [
    {"topic_id": "topic.query.result", "audience": "business", "source_document": "常见问答.md", "source_heading": "查询结果"}
  ],
  "nodes": [],
  "links": [],
  "identity_history": []
}
```

入口、接口、方法、事实继续使用现有 `entry_id`、`api_id`、`method_id`、`fact_id`；跨模块事实引用写为 `module_id#fact_id`，目前仅允许用于“事实→主题”连接，校验时必须在被引用模块的规格中找到该事实。覆盖报告按模块展示本地连接，跨模块引用另以清单中的完整 ID 追溯。`topic_id` 是人工保持稳定的主题身份，当次发布的 `unit_id` 可以随标题变化。重命名保留身份；事实语义更换、拆分或合并时创建新 ID，在 `identity_history` 记录旧 ID、新 ID 列表和原因。事件、任务、配置、字段如有实际证据，可在 `nodes` 中登记；没有证据不造节点。

连接类型仅允许入口→接口、接口→方法、方法→事实、事实→主题，以及事件/任务→方法、配置/字段→事实。每条连接含两端类型与 ID、`status`、`evidence`、`reviewed_by` 和 `reviewed_at`。`verified` 必须附固定提交证据快照及复核身份、日期；`candidate`/`unresolved` 不得填写已证实复核标记。旧规格的“疑似匹配”只生成候选，“未匹配”和“外部依赖”保持未解；即使两侧行号存在，也不能自动升级为已证实。

## 固定提交证据

用 `code2kb evidence-snapshot --project-root <知识项目> --anchor 仓库ID:相对路径:起始行-结束行` 生成证据记录，复制到连接的 `evidence` 列表。单行可写 `仓库ID:相对路径:行号`。记录含完整提交、路径、行段、片段 SHA-256 和 Git blob identity。工具从固定提交读取，工作区和后续提交不会改变旧证据。切换取证提交后，旧记录须重新核对；相似文字搜索只能给出候选新位置。

证据重建只证明该提交中的文本与身份。它不能证明运行结果、部署配对、动态取值、业务动机或审核者现实身份。仅有检索命中也不能证明模型最终答复正确。

升级源码提交前，可以运行 `code2kb preview-upgrade --project-root <知识项目> --module-id <模块ID> --repository-id <仓库ID> --new-commit <新提交>`。它先在旧提交重建映射内的显式证据，再尝试在新提交的原位置读取，报告需要重核的连接、直接关联的事实和主题；不修改配置或证据。报告只覆盖显式映射中的证据，不能代替全量变化分析。旧提交的证据在工作区改变或新提交出现后仍保持有效；切换配置时才需要重新定位和复核。

## 审核与发布

1. 修改映射后运行 `impact`。工具将映射摘要加入关系影响队列。
   `code2kb relation-report --project-root <知识项目> --module-id <模块ID>` 列出尚无已证实连接的入口、接口、方法、事实与主题；候选连接不算完成覆盖。
2. 核对事实、映射和正文后运行现有 `confirm-claims`，在规格中记录关系复核摘要。
3. 重新 `prepare --refresh`，关系映射摘要进入发布清单的审核依据。按既有授权流程批准并提交全部发布输入。
4. `publish` 随基础发布冻结映射输入，在 `发布/关系清单/` 写派生清单与独立指针；如果同时发布检索版，关系清单也绑定检索清单摘要及对应单元。`audit-release` 检查这些文件的摘要与路径；`code2kb relation-audit --project-root <知识项目> --release-id <发布ID>` 明确要求关系扩展存在并审计它。

发布物内的关系审计检查冻结快照一致性；**不持有源码仓库时不能重建源码证据**，审计结果会明确报告这一限制。关系扩展采用独立指针，基础版本清单不绑定它；若把全部关系扩展产物一起删除，常规基础审计只能确认基础发布仍完整，应另运行 `relation-audit` 检查扩展是否存在。工作目录仍只保留当前发布，旧版本需从对应 Git 提交或标签恢复后审计；知识源工作稿随后变化不影响已冻结的旧发布。`analyze-candidates` 只输出固定提交中的 UniApp/TypeScript 和 Java 静态候选，不写事实或批准状态。

## 同一事实的三处结论段

模块可选择在结构化规格的 `## 规范化事实` 表中给已存在的事实补充适用条件、结论、例外与未知边界。运行 `code2kb render-facts --project-root <知识项目> --module-id <模块ID>`，工具只输出 JSON 候选段：业务段不含内部事实编号，研发段带事实与源码导航，检索段沿用同一条件、结论和未知边界并附来源。作者把候选段纳入对应正文后仍须复核、运行影响检查和更新发布包。旧项目不填写该表时正文及检索生成行为不变。
