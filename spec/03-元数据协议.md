# 元数据协议

本章完整定义知识项目的机器可读元数据。模板用于示例，参考实现用于校验；两者都不得替代本章的字段契约。

## 序列化规则

知识 Markdown 使用 UTF-8、单层 YAML 风格 front matter。首行和结束行均为 `---`，中间每行只能是“小写下划线键: 字符串值”。键不得重复；值按去除首尾空白和成对单引号或双引号后的字符串读取。列表使用英文逗号分隔，摘要使用 64 位小写 SHA-256。

JSON 文件必须为 UTF-8 对象，键不得重复。除本章明确允许的字段外，配置、审核策略、审核记录、版本清单和当前版本指针不得含未知字段。

## Markdown 通用字段

| 字段 | 适用范围 | 取值与要求 |
| --- | --- | --- |
| `document_type` | 全部知识 Markdown | 必填；必须与下表文件名一致 |
| `module_id` | 模块与场景文件 | 必填；`[a-z][a-z0-9_.-]*` |
| `scene_id` | 场景目录文件 | 必填；模块根目录文件不得借此伪装场景 |
| `review_status` | 全部知识 Markdown | 必填；`draft`、`reviewed`、`policy_reviewed` |
| `applicability` | 全部知识 Markdown | 必填；`current`、`superseded` |
| `aliases` | 业务正文 | 可选；用于检索的逗号分隔别名，不得承载技术或过程词 |
| `source_revisions` | 大纲、规格、研发文件及运行/部署证据 | `仓库ID=固定SHA` 的逗号分隔列表；仓库 ID 排序且不重复，只列本文件实际引用的仓库 |
| `runtime_status` | 已审核研发文件 | `source_only`、`runtime_verified`、`verified_deployment` |
| `runtime_evidence` | `runtime_verified` 研发文件 | 逗号分隔的运行或部署证据 ID；不得用业务确认证据代替 |
| `deployment_evidence` | `verified_deployment` 研发文件 | 对应部署证据 ID；没有部署配对证据不得填写该状态 |

人工审核字段：`reviewed_by`、`reviewed_at`。日期使用 `YYYY-MM-DD`；`reviewed` 状态两者都必填。

策略审核字段：`review_mode: policy_auto`、`review_policy`、`policy_version`、`policy_owner`、`executed_by`、`reviewed_at`、`review_evidence`、`review_evidence_digest`、`policy_digest`。`policy_reviewed` 状态全部必填，两个摘要均为 SHA-256，且不得出现 `reviewed_by`。

## 文件名与 document_type

| 文件名或位置 | `document_type` | 类别 | 专用字段 |
| --- | --- | --- | --- |
| `功能大纲.md` | `outline` | 治理 | `source_revisions`、`inventory_status: draft|complete` |
| `术语表.md` | `glossary` | 业务 | 通用字段；位于知识源根目录时不填 `module_id` |
| `模块概览.md` | `overview` | 业务 | 通用字段 |
| `功能与范围.md` | `scope` | 业务 | 通用字段 |
| `业务流程.md` | `flow` | 业务 | 通用字段 |
| `规则与限制.md` | `rules` | 业务 | 通用字段 |
| `常见问答.md` | `faq` | 业务 | 通用字段 |
| `业务意图.md` | `intent` | 业务 | 通用字段；只容纳已闭环意图 |
| `技术实现.md` | `implementation` | 研发 | `runtime_status`、`source_revisions`，必要时 `deployment_evidence` |
| `接口与调用.md` | `api_catalog` | 研发 | 同上 |
| `方法与源码.md` | `method_catalog` | 研发 | 同上 |
| `结构化规格.md` | `spec` | 治理 | `source_revisions` |
| `待确认事项.md` | `questions` | 治理 | 通用字段 |
| `发布清单.md` | `release_manifest` | 治理 | 见下节 |

业务正文只允许业务通用字段和对应审核字段，不得加入源码提交、运行状态或部署证据。研发文件在 `draft` 时可以缺少 `runtime_status`；进入任一已审核状态前必须补齐。

## 发布清单字段

`prepare` 生成发布清单，并填写以下候选字段：

| 字段 | 要求 |
| --- | --- |
| `intent_included` | `true` 或 `false`，必须与候选中是否包含 `业务意图.md` 一致 |
| `business_topics`、`business_unknowns`、`business_keywords` | 业务版主题、未知边界和检索词；不得含技术或过程用语 |
| `engineering_topics`、`engineering_unknowns`、`engineering_keywords` | 研发版对应内容 |
| `review_subject_digest` | 候选内容和边界的 SHA-256；后加审核戳不改变其计算对象 |

人工批准后，清单增加 `approval_note` 和 `approval_snapshot`；策略审核后增加 `policy_review_snapshot` 及策略审核字段。摘要绑定失效后必须回到 `draft` 并重新准备。

## 证据元数据

全部证据使用：`document_type: runtime_evidence`、`evidence_id`、`module_id`、`evidence_type`、可选 `applicability`（省略时视为 `current`）、`environment`、`observed_at`、可选 `valid_until` 和 `fact_ids`。`evidence_type` 取 `runtime`、`deployment` 或 `business`；日期为 `YYYY-MM-DD`；`evidence_id` 以 `EVID-` 开头。运行与部署证据必须另外绑定 `source_revisions`。

业务材料证据额外使用且必须填写：`source_type: document|human`、`source_title`、`source_locator`、`source_sha256`、`content_mode: redacted_excerpt`、`intent_ids` 和 `valid_until`。`source_type: human` 还必须填写 `confirmed_by`、`confirmed_at`、`confirmation_note`。业务材料原文不得因建立证据记录而复制进 Git。

## 知识库配置.json

- **C2KB-META-001**：`知识库配置.json` 必须是 UTF-8 JSON 对象，禁止重复字段和未知顶层字段。
- **C2KB-META-002**：`standard_version` 必须为受支持的公开文件协议标识：`c2kb-file/1` 或历史兼容标识 `0.8.3`。未知标识必须拒绝。
- **C2KB-META-003**：每个仓库必须包含唯一仓库 ID、绝对路径或完整 `${UPPER_CASE_ENV}` 引用，以及固定 Git SHA。
- **C2KB-META-004**：环境变量只能替代整个路径值；禁止 shell 展开、命令替换、默认值表达式和变量拼接。
- **C2KB-META-005**：固定提交禁止使用环境变量或分支名。
- **C2KB-META-006**：人工审核字段与策略审核字段禁止混用。
- **C2KB-META-007**：`reviewed` 必须记录审核人和日期；`policy_reviewed` 必须记录策略、授权人、执行者、证据路径及摘要。

允许的配置顶层字段如下：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `standard_version` | 字符串 | 必填；新项目写 `c2kb-file/1`，现有项目可保留 `0.8.3` |
| `knowledge_source_root` | 字符串 | 必填，项目内安全相对目录 |
| `repositories` | 对象 | 必填且非空；键为仓库 ID，值严格包含 `path`、`commit` |
| `coverage_terms` | 字符串数组 | 可选；每项非空 |
| `sensitive_patterns` | 字符串数组 | 可选；每项为有效正则 |
| `boundary_notes` | 对象 | 可选；只允许字符串字段 `business`、`engineering` |
| `inventory_adapter` | 对象 | 可选；见下文 |
| `policy_review` | 对象 | 可选；见下文 |
| `semantic_quality` | 对象 | 可选；见下文 |

`inventory_adapter` 只允许 `name`、`repository`、`manifest_path`、`entry_type`；兼容项目保留参考适配器名称 `uniapp_pages`，仓库必须已配置，清单路径必须为安全相对路径。0.7 候选扫描输出通过命令参数显式启用，不暗改已有项目配置。`policy_review` 只允许布尔 `enabled` 与可选 `policy_file`；启用时策略文件必须是项目内相对 JSON。`semantic_quality` 必须严格包含布尔 `enabled` 与非空、不重复的 `module_ids`；模块列表可以是单独的 `"*"`。

## 自动审核 JSON

策略对象字段必须恰好为：`schema_version`、`policy_id`、`policy_version`、`policy_owner`、`authorized_at`、`authorization_note`、`expires_at`、`allowed_module_ids`、`allowed_risk_levels`、`required_checks`、`manual_gate_categories`。`schema_version` 为 `1.0`，策略版本为三段数字；日期为 `YYYY-MM-DD`；所有数组非空且不重复。

审核记录字段必须恰好为：`schema_version`、`run_id`、`module_id`、`policy_id`、`policy_version`、`review_subject_digest`、`risk_level`、`source_revisions`、`checks`、`findings`、`external_reports`、`completed_at`、`executed_by`。`checks` 中每项绑定检查 ID、通过状态和报告摘要；`findings` 必须使用允许的处置状态；外部报告只校验声明、路径与摘要绑定，不证明报告自然语言真实。

## 发布 JSON

版本清单的 `registry_schema_version` 为 `2.0`，字段必须恰好为：`standard_version`、`registry_schema_version`、`release_id`、`document_commit`、`generated_by`、`created_at`、`review_summary`、`module_reviews`、`views`。`views` 严格包含 `business` 和 `engineering`；每个视图严格包含项目内发布路径 `path` 与“相对文件路径 → SHA-256”的非空 `files` 对象。

当前版本指针字段必须恰好为：`standard_version`、`release_id`、`business_path`、`engineering_path`、`document_commit`、`registry_path`、`registry_sha256`、`history_backend`、`generated_by`。`history_backend` 为 `git`；其余身份、路径和摘要必须与版本清单一致。

## 规范与实现的关系

实现可以增加诊断信息和命令行选项，但不得放宽本章的必填字段、值域、互斥关系或摘要绑定。第三方实现无需复制 Python 代码；只要对相同一致性夹具给出相同的有效/无效结论，并声明覆盖的 `C2KB-*` 编号，即可提出兼容声明。
